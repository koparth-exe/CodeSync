APPROVED WITH TARGETED COMPATIBILITY EVIDENCE GAPS

The CodeSync architecture demonstrates strong cross-browser compatibility across its supported Chromium MV3 and Firefox MV3 targets. Core abstractions—including the two-tier concurrency engine (Web Locks + persistent leasing with fencing tokens), Write-Ahead Logging (WAL) in IndexedDB, immutable `TargetSnapshot` capture, deterministic three-pillar path canonicalization, and cryptographic SHA-256 content hashing—are built on standardized Web platform and WebExtension APIs.

## 4. Architecture Review

### Manifest Generation & WXT Framework
- Built with **WXT 0.21.4** and Vite 8.3.0.
- WXT handles browser-specific manifest differences automatically:
  - Chrome manifest compiles `"background": {"service_worker": "background.js"}`.
  - Firefox manifest compiles `"background": {"scripts": ["background.js"]}`.
- Both targets enforce an identical, strictly hardened Content Security Policy (CSP):
  `script-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; style-src 'self' 'unsafe-inline';`

### Runtime APIs & Namespace Abstraction
- CodeSync utilizes WXT's unified `browser.*` global namespace polyfill while providing explicit fail-closed fallbacks in `src/shared/browser/index.ts` (`getExtensionRuntime` and `getExtensionStorage`).
- If called outside a valid extension context, both helpers throw typed `BrowserRuntimeError` with `failClosed: true`.

### Messaging & Sender Verification
- Content scripts dispatch candidates via `browser.runtime.sendMessage(message)`.
- Background service worker listens via `browser.runtime.onMessage.addListener(..., sendResponse)`.
- Async response semantics use `return true;` to keep message channels open across asynchronous validation and enqueue operations.
- Sender context derivation (`deriveTrustedSenderContext`) uses authoritative runtime metadata (`runtimeSender.tab` for content scripts, extension URL `.includes("popup.html")` for popup). It is completely browser-agnostic and immune to `chrome-extension://` vs `moz-extension://` prefix differences.

### Content Scripts & Platform Adapters
- Content scripts execute in isolated worlds on both engines.
- Adapters use passive event listeners (`click`, `popstate`) and bounded debounced `MutationObserver` (300ms) to detect submissions without mutating or depending on webpage globals.
- Platform extraction produces candidate models with `TrustBoundary.SEMI_TRUSTED`; validation authority resides strictly in the service worker.

### Service Worker vs Event Page Lifecycle
- Chromium executes `background.ts` in a `ServiceWorkerGlobalScope` (no DOM/window, aggressive idle suspension after ~30s of inactivity).
- Firefox executes `background.ts` in a background event page (DOM window available, event-driven idle unloading).
- CodeSync's background logic strictly avoids DOM/window access, global state retention, or unpinned timers.
- Handlers (`createGitHubQueueItemHandler`) are registered synchronously at top-level initialization, ensuring immediate readiness when woken by alarms or messages.

### Storage Architecture
- **Lightweight State (`browser.storage.local`)**:
  - Stores queue metadata (`QueueItemMetadata[]`), persistent leases (`QueueLeaseRecord`), auth states (`GitHubAuthState`), and extension settings (`ExtensionConfig`).
  - Serialized cleanly as JSON objects.
- **Heavy State (IndexedDB `codesync_db`)**:
  - Stores source code payloads (`payloads`), sync history (`history`), and intent-first Write-Ahead Logs (`wal_logs`).
  - Standard W3C IndexedDB API supported natively in Chromium Service Workers and Firefox Event Pages.

### Concurrency & Web Locks
- `QueueConcurrencyManager` and `DurableTokenLifecycleManager` implement a two-tier concurrency model:
  - **Tier 1**: `navigator.locks.request` with exclusive mode.
  - **Tier 2**: Persistent lease record in `storage.local` with monotonic `fencingToken` and 30s TTL heartbeats.
- Web Locks are supported in both Chrome 116+ and Firefox 128+. In environments where Web Locks fail or are unavailable, Tier 2 leasing and fencing provide durable correctness.

### Alarms & Periodic Drains
- Periodic drain alarm (`codesync_queue_drain_alarm`) registered via `browser.alarms.create` with `periodInMinutes: 5`.
- Deduplicated on install/startup (`setupQueueDrainAlarm`).
- In addition to alarms, queue drains trigger on startup (`drain("startup")`) and submission events (`drain("submission_event")`).

### Network & Fetch
- Standard `fetch` utilized for GitHub API operations with `cache: "no-store"`.
- Token lifecycle coordination (`DurableTokenLifecycleManager`) handles 401 refresh with epoch fencing.
- Network dropouts during write dispatch are caught and reconciled (`reconcileUncertainWrite`) via authoritative GET before declaring outcomes.

### Cryptography & Encodings
- `crypto.randomUUID()`: W3C standard, supported identically in V8 and SpiderMonkey.
- `crypto.subtle.digest("SHA-256", ...)`: Identical cryptographic output across engines.
- `String.prototype.normalize("NFKC")`: Uniform Unicode normalization.
- `safeBase64Encode`: Custom UTF-8 byte encoder avoids `btoa` latin1 exceptions.

## 10. Evidence Gaps

### YELLOW-01: Runtime Messaging Asynchronous Response & Channel Lifetime Parity
- **Risk**: In `background.ts`, `browser.runtime.onMessage.addListener` uses `return true;` to maintain an asynchronous channel while `handleMessageAndEnqueue` executes. In Chromium MV3 service workers, idle timers reset on active events, but if an event page in Firefox unloads or a service worker terminates unexpectedly during high-latency operations, the port can close prematurely.
- **Evidence Need**: Verification that async candidate ingestion and enqueue return responses reliably without channel-closure errors across both simulated environments.

### YELLOW-02: Background Execution Context & Worker Restart Parity
- **Risk**: Chrome MV3 compiles to a Service Worker (`ServiceWorkerGlobalScope`), whereas Firefox MV3 compiles to an Event Page (`scripts: ["background.js"]`). While CodeSync avoids `window` references in background scripts, the recovery behavior upon worker restart (re-registering handlers, re-triggering alarms, reconciling crashed items) must be verified to behave identically across both context types.
- **Evidence Need**: Verification that a background context suspension and cold restart restores handlers, initializes alarms, and reconciles interrupted queue items identically under both Service Worker and Event Page models.

### YELLOW-03: Web Locks Availability & Persistent Lease Fencing Fallback Parity
- **Risk**: `QueueConcurrencyManager` and `DurableTokenLifecycleManager` query `supportsWebLocks`. While modern Chrome and Firefox both support Web Locks, private browsing modes or constrained extension environments can disable Web Locks.
- **Evidence Need**: Verification that when `supportsWebLocks` is false, the Tier 2 persistent lease and monotonic fencing token completely and safely govern mutual exclusion without deadlock.

### YELLOW-04: Storage Driver Error Propagation & Fail-Closed Boundary
- **Risk**: `WebExtensionStorageDriver` (`src/shared/storage/local.ts`) wraps `storage.local.get/set/remove` in callbacks checking `chrome?.runtime?.lastError`. In Firefox native WebExtension environments where `browser.storage.local` returns native Promises, error propagation must fail closed cleanly with typed `StorageError` rather than unhandled rejections.
- **Evidence Need**: Verification that storage quota exhaustion or storage errors throw typed `StorageError` fail-closed under both callback and Promise-based driver configurations.

### YELLOW-05: Undeclared Minimum Chromium Version Specification
- **Risk**: `wxt.config.ts` declares `browser_specific_settings.gecko.strict_min_version: "128.0"`, but leaves Chromium unversioned. Users running obsolete Chromium releases (<109 or <116) could encounter missing Service Worker APIs or unstable Web Locks.
- **Evidence Need**: Explicit declaration and validation of `minimum_chrome_version: "116"` in extension configuration.

## 11. Required Targeted Tests

To close the five evidence gaps above, exactly four targeted compatibility integration tests are specified for Phase 1C.4.3.6.1:

1. **`CB-INT-01`: Runtime Messaging Channel & Async Response Parity**
   - **Target**: `background.ts` -> `MessageEnvelopeValidator` -> `SubmissionHandler.handleMessageAndEnqueue`
   - **Objective**: Verify that asynchronous `SUBMISSION_DETECTED` message handling completes, enqueues work, returns typed success/failure envelopes, and keeps the channel open without port-closure errors across simulated Chromium and Gecko environments.
2. **`CB-INT-02`: Background Execution Context & Worker Restart Parity**
   - **Target**: `background.ts` initialization -> `defaultQueueDrainer.setHandler` -> `reconcileInterruptedItems`
   - **Objective**: Verify that simulating background context termination and cold restart (Service Worker vs Event Page) synchronously restores queue item handlers, triggers initial drain, and reconciles interrupted items without state corruption.
3. **`CB-INT-03`: Web Locks & Persistent Lease Fencing Fallback Parity**
   - **Target**: `QueueConcurrencyManager.runExclusively` & `DurableTokenLifecycleManager`
   - **Objective**: Verify that when `supportsWebLocks` is false (simulating disabled/unsupported Web Locks in constrained environments), Tier 2 persistent leasing and monotonic fencing tokens acquire locks, process items, renew heartbeats, and reject stale workers fail-closed.
4. **`CB-INT-04`: Storage Driver Error Propagation & Fail-Closed Parity**
   - **Target**: `WebExtensionStorageDriver` & `StorageService`
   - **Objective**: Verify that storage errors (`lastError` in Chrome and rejected Promises in Gecko) are translated into typed `StorageError` with `ErrorCode.STORAGE_ERROR` / `STORAGE_UNAVAILABLE` and fail closed.

## 12. Browser-Specific Risks

### Confirmed Behavior
- **Manifest Background Types**: Chrome MV3 generates `service_worker: "background.js"`; Firefox MV3 generates `scripts: ["background.js"]`. Confirmed via `.output` build artifacts.
- **Extension ID & Gecko Settings**: Firefox requires an explicit extension ID for MV3 debugging and store submission (`codesync@extension.local`). Confirmed present in `wxt.config.ts`.
- **W3C Crypto & Hashing**: `crypto.subtle` and `crypto.randomUUID()` operate identically in Chromium V8 and Firefox SpiderMonkey.

### Documented Behavior
- **Firefox MV3 Event Pages**: Mozilla documentation specifies that Firefox MV3 extensions default to event pages rather than service workers, preserving standard background script capabilities while maintaining event-driven idle unloading.
- **Chromium MV3 Service Workers**: Google Chrome documentation specifies that service workers are suspended after 30 seconds of inactivity and terminate all active execution.

### Repository Evidence
- **Browser Abstraction**: `src/shared/browser/index.ts` safely inspects `navigator.userAgent` and provides `detectBrowser()` and `getBrowserCapabilities()`.
- **Durable Concurrency**: Concurrency relies on durable leases in `storage.local` and IndexedDB, ensuring worker suspension does not compromise state.

### Inferred Behavior (Requires Verification)
- **Idle Channel Lifetimes**: Whether rapid idle suspension during heavy queue drains can lead to unhandled message channel closures in Chrome vs Firefox. Addressed by `CB-INT-01`.
