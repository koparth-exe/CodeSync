## 2. Previous State

- **minimum_chrome_version**: `"116"`
- **reason previously given**: "Modern MV3 Service Worker alarms, Web Locks, and dynamic imports require Chrome 116+ (ESR / mainstream baseline)."
- **why that evidence was insufficient**:
  1. `chrome.alarms` in MV3 was introduced in Chrome 88 (not Chrome 116).
  2. Web Locks API (`navigator.locks`) was introduced in Chrome 69 (not Chrome 116).
  3. Dynamic imports (`import(...)`) are **not used** anywhere in the CodeSync codebase.
  4. Chrome 116 added WebSocket keepalives in service workers, strong keepalives for user-prompt extension APIs, and `chrome.runtime.getContexts()`. CodeSync uses none of these features.
  5. Selecting 116 was an arbitrary modern baseline chosen for symmetry with Firefox ESR 128 rather than the earliest version required by CodeSync's actual code.

## 4. Messaging Analysis

- **actual implementation**: Top-level registration in [src/entrypoints/background.ts](file:///d:/Parth/Projects/CodeSync/src/entrypoints/background.ts#L104) via `browser.runtime.onMessage.addListener((message, sender, sendResponse) => { ...; return true; })`. Content scripts dispatch messages using `browser.runtime.sendMessage(message)`.
- **Chrome-specific dependency**: Synchronous `return true;` instructs the Chromium message dispatcher to keep the message port open until asynchronous validation and enqueueing complete, followed by `sendResponse(result)`.
- **minimum relevant version**: **Chrome 88** (Manifest V3 Service Worker baseline).
- **conclusion**: CodeSync relies strictly on the standard callback-based `sendResponse` pattern with `return true;`. It does NOT return Promises from `onMessage` listeners in Chromium and does NOT depend on any messaging behavior introduced in Chrome 116.

---

## 5. Web Locks Analysis

- **mandatory/optional**: **Optional** (Tier 1 opportunistic optimization).
- **fallback**: Full, fail-closed fallback to Tier 2 persistent lease in `browser.storage.local` with monotonic fencing tokens and heartbeats (`executeWithLease()`).
- **Chrome-specific dependency**: None. Tier 2 persistent lease provides 100% correctness even when `navigator.locks` is completely absent (`undefined`), as authoritatively demonstrated in test `CB-INT-03`.
- **minimum relevant version**: Chrome 69 (when Web Locks are present); Chrome 88 (when running purely on Tier 2 persistent lease in MV3).
- **conclusion**: Web Locks is an optional performance layer. Its presence in Chrome 69+ does not raise the minimum version requirement beyond other core dependencies.

---

## 6. Service Worker Analysis

- **actual lifecycle dependency**: Top-level event listener registration (`onInstalled`, `onStartup`, `onAlarm`, `onMessage`) during initial script evaluation. Alarms periodically wake the service worker.
- **durable-state protection**: CodeSync adheres strictly to a local-first, durable-state architecture. In-memory state is non-authoritative; all critical state (queue items, WAL intent logs, source payloads, leases, and authentication tokens) is persisted durably to `browser.storage.local` and `IndexedDB`.
- **Chrome-specific dependency**: CodeSync does NOT rely on keeping service workers alive indefinitely. Interrupted operations are cleanly reconciled upon cold restart (`CB-INT-02`). It does NOT use WebSocket keepalives, user-prompt strong keepalives, or `chrome.runtime.getContexts()` introduced in Chrome 116.
- **minimum relevant version**: **Chrome 88** (MV3 Service Worker introduction).
- **conclusion**: CodeSync is architected specifically to be immune to aggressive service worker termination. Chrome 116's service worker lifetime adjustments are completely unnecessary for CodeSync's correctness.

## 7. GAP-05 Decision

- **Required minimum Chromium version**: `"92"`
- **Previous configured version**: `"116"`
- **Final configured version**: `"92"`
- **Technical Explanation**:
  1. **Manifest V3 Baseline**: Requires Chrome >= 88.
  2. **The Hard Lower Bound (`crypto.randomUUID`)**: CodeSync calls `crypto.randomUUID()` unconditionally across 6 production files (`content.ts`, `submission-handler.ts`, `manager.ts`, `concurrency.ts`, `token-lifecycle.ts`, `local.ts`) with **zero fallback**. On Chrome versions 88 through 91, `crypto.randomUUID` is `undefined`, causing immediate fatal `TypeError` exceptions during candidate extraction, enqueueing, or background worker startup. Native `crypto.randomUUID()` was added to Chromium in **Chrome 92**.
  3. **Upper Bound Sufficiency**: All other APIs utilized by CodeSync (Web Locks: Chrome 69; Web Crypto SHA-256: Chrome 40; IndexedDB: Chrome 40; fetch in SW: Chrome 42; AbortController: Chrome 66; alarms: Chrome 88; storage: Chrome 88) were available at or before Chrome 92. CodeSync uses no ECMAScript syntax or browser APIs introduced after Chrome 92.
  4. **Conclusion**: Chrome 92 is the earliest Chromium version on which the actual CodeSync implementation can safely and correctly operate.

## 8. Evidence

1. **`crypto.randomUUID()` in Chrome 92**:
   - **Source**: [MDN Web Docs — Crypto: randomUUID() method](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID) & Chromium issue tracker.

   - **Relevant Version**: Chrome 92 (Release date: July 20, 2021).
   - **Implication for CodeSync**: Core requirement. Missing on Chrome < 92; fully supported on Chrome >= 92.

   - **Relevant Feature**: Manifest V3 format, `"background": { "service_worker": "..." }`, extension alarms, and declarative permissions.
   - **Relevant Version**: Chrome 88 (Release date: January 19, 2021).
   - **Implication for CodeSync**: CodeSync's `manifest_version: 3` requires at least Chrome 88.
3. **Web Locks in Workers**:
   - **Source**: [MDN Web Docs — Navigator: locks property](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/locks).
   - **Relevant Feature**: `navigator.locks.request` in Window and Worker scopes.
   - **Relevant Version**: Chrome 69 (Release date: September 4, 2018).
   - **Implication for CodeSync**: Satisfied well before Chrome 92.
4. **AbortController in Chromium**:
   - **Source**: [MDN Web Docs — AbortController](https://developer.mozilla.org/en-US/docs/Web/API/AbortController).
   - **Relevant Feature**: Request abort signaling with `new AbortController()`.
   - **Relevant Version**: Chrome 66 (Release date: April 17, 2018).
   - **Implication for CodeSync**: Satisfied well before Chrome 92.
