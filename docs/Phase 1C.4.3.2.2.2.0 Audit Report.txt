# Phase 1C.4.3.2.2.2.0 Audit Report

## 1. Executive Summary

This document presents the formal repository audit for **Phase 1C.4.3.2.2.2.0 — Write-Ahead Log (WAL), Orphan, and Interrupted-State Recovery** in CodeSync.

The primary objective of this audit is to evaluate whether CodeSync can safely, deterministically, and idempotently reconstruct durable state after service-worker terminations, unhandled crashes, partial write boundaries, power interruptions, or corrupted durable states.

### Core Recovery Invariant
```
CRASH / INTERRUPTION
        ↓
DURABLE STATE MAY BE PARTIAL
        ↓
RECOVERY RECONCILIATION
        ↓
DETERMINISTIC STATE
        ↓
SAFE CONTINUATION OR REQUIRES_ATTENTION
```

### Key Findings
1. **Durable Intent-First WAL**: Enqueue operations strictly follow an intent-first protocol (`INTENT` written to IndexedDB `wal_logs` **before** payload persistence in IndexedDB and metadata write in `browser.storage.local`).
2. **Fail-Closed Orphan Recovery**:
   - **Orphan Payloads** (IndexedDB payload with missing queue metadata) are **never silently discarded** or blindly pushed to GitHub; they are safely quarantined into `QueueState.REQUIRES_ATTENTION` with status `"RECOVERED_ORPHAN_PAYLOAD"` and `ErrorCode.INVARIANT_VIOLATION`. User source code remains 100% intact.
   - **Orphan Metadata** (metadata pointing to a missing IndexedDB payload) transitions immediately to `QueueState.REQUIRES_ATTENTION` with `ErrorCode.PAYLOAD_NOT_FOUND`. It is never retried or sent to GitHub.
3. **Bounded Poison-Pill Quarantine**: Interrupted items in `QueueState.PROCESSING` have their `crashCount` incremented. At `crashCount >= 3` (`POISON_PILL_CRASH_THRESHOLD`), items are quarantined to `QueueState.REQUIRES_ATTENTION` with `ErrorCode.POISON_PILL_DETECTED`. Prior to 3 crashes, items revert to `QueueState.PENDING` without consuming network retry attempts.
4. **Durable Retry & Rate-Limit Preservation**: Rate-limit reset timestamps (`nextRetryAt`) and attempt counters survive worker crashes because they are persisted directly in `QueueItemMetadata`.
5. **No Blind Remote Overwrites**: Uncertain GitHub writes across worker terminations are reconciled via pre-flight `GET` requests and content-hash comparison, ensuring zero duplicate `PUT` operations.
6. **Persistent Lease & Fencing Enforcement**: Recovery and queue processing execute under exclusive lease authority (`QueueConcurrencyManager.runExclusively`) guarded by monotonic fencing tokens, rejecting stale worker mutations.
7. **Baseline Metrics**: The repository compiles cleanly with 0 TypeScript errors, 0 ESLint warnings, 0 Prettier formatting discrepancies, builds both Chrome and Firefox MV3 bundles, and passes all **471 automated tests** across 37 test files.

## 4. WAL Architecture

CodeSync utilizes a **hybrid partitioned storage model**:
- **Lightweight Metadata**: Stored in `browser.storage.local` under `codesync:queue:metadata` for low-latency querying, alarm wakeups, and queue size evaluation.
- **Heavy Code Payloads**: Stored in IndexedDB object store `payloads` under key `payload:<id>` to avoid exceeding Chrome's 5 MB / 10 MB `storage.local` quota.
- **Write-Ahead Log (WAL)**: Stored in IndexedDB object store `wal_logs` under key `opId` (`UUID`).

### Intent-First Architecture
Because Web Extensions cannot execute multi-store atomic transactions across `browser.storage.local` and `IndexedDB`, an intent-first WAL is necessary to bridge crash boundaries:

```
[Enqueue Request]
       │
       ▼
1. Validate bounds (< 200 items) & Deduplication check
       │
       ▼
2. Write WAL entry (phase: INTENT, snapshot: submission) -> IndexedDB (wal_logs)
       │
       ▼
3. Write payload (sourceCode) -> IndexedDB (payloads)
       │
       ▼
4. Write metadata (state: PENDING) -> storage.local
       │
       ▼
5. Update WAL entry (phase: COMMITTED) -> IndexedDB (wal_logs)
       │
       ▼
6. Delete WAL entry -> IndexedDB (wal_logs)
```

If a crash occurs at any step, the next worker running `reconcileWalAndOrphans()` can determine the exact phase and reconstruct a consistent state.

## 6. WAL Write Ordering

The audit traced all crash boundaries across the enqueue write lifecycle:

```
[Crash W1]           [Crash W2]             [Crash W3]            [Crash W4]
    │                    │                      │                     │
    ▼                    ▼                      ▼                     ▼
WAL INTENT ──► PAYLOAD PERSISTED ──► METADATA PERSISTED ──► WAL COMMITTED ──► WAL DELETED
```

### Boundary Trace
- **W1 (WAL intent persisted → crash before payload persistence)**:
  - *Durable State*: WAL exists (`phase: INTENT`). Payload: missing. Metadata: missing.
  - *Recovery Action*: `reconcileWalAndOrphans()` detects `INTENT` without payload; safely prunes residual WAL record. Zero phantom metadata created.
- **W2 (WAL intent persisted → payload persisted → crash before metadata persistence)**:
  - *Durable State*: WAL exists (`phase: INTENT`, `snapshot.submission`). Payload exists in IndexedDB. Metadata missing in `storage.local`.
  - *Recovery Action*: `reconcileWalAndOrphans()` reconstructs `QueueItemMetadata` from `wal.snapshot.submission`, sets `state: PENDING`, `crashCount: 1`, writes metadata to `storage.local`, and deletes WAL entry. Zero data loss.
- **W3 (WAL intent persisted → payload persisted → metadata persisted → crash before WAL committed)**:
  - *Durable State*: WAL exists (`phase: INTENT`). Both payload and metadata exist.
  - *Recovery Action*: Recovery detects both metadata and payload exist; cleanly deletes residual WAL record.
- **W4 (Metadata persisted → WAL committed → crash before WAL deletion)**:
  - *Durable State*: WAL exists (`phase: COMMITTED`). Metadata and payload exist.
  - *Recovery Action*: `wal.phase === COMMITTED` check fires; safely deletes WAL record.
- **W5 (Metadata persisted → payload deletion boundary during purge)**:
  - *Durable State*: Purge operation WAL. Metadata purged or payload purged.
  - *Recovery Action*: Cleaned up idempotently.
- **W6 (Recovery itself interrupted mid-execution)**:
  - *Durable State*: Partial recovery mutations committed to `storage.local`.
  - *Recovery Action*: Subsequent recovery pass resumes from deterministic durable state without creating duplicates.

## 10. Interrupted PROCESSING Recovery

### Specification & Code Path
Trace: [`src/shared/queue/manager.ts:297-332`](file:///d:/Parth/Projects/CodeSync/src/shared/queue/manager.ts#L297-L332).

```typescript
export const POISON_PILL_CRASH_THRESHOLD = 3;

async reconcileInterruptedItems(): Promise<InterruptedReconciliationSummary> {
  const summary: InterruptedReconciliationSummary = {
    reconciledCount: 0,
    quarantinedCount: 0,
  };

  const queue = await this.storage.getQueueMetadata();
  let modified = false;

  for (const item of queue) {
    if (item.state === QueueState.PROCESSING) {
      modified = true;
      item.crashCount = (item.crashCount ?? 0) + 1;
      item.updatedAt = Date.now();

      if (item.crashCount >= POISON_PILL_CRASH_THRESHOLD) {
        item.state = QueueState.REQUIRES_ATTENTION;
        item.lastError = {
          code: ErrorCode.POISON_PILL_DETECTED,
          message: `Queue item repeatedly caused worker crash (${item.crashCount} crashes). Quarantined.`,
          timestamp: Date.now(),
        };
        summary.quarantinedCount++;
      } else {
        item.state = QueueState.PENDING;
        summary.reconciledCount++;
      }
    }
  }

  if (modified) {
    await this.storage.setQueueMetadata(queue);
  }

  return summary;
}
```

### Interrupted State Lifecycle

```
PENDING ──► PROCESSING (Worker crashes)
                 │
                 ▼
          [Fresh Worker Startup]
                 │
                 ├── crashCount < 3 ──► PENDING (reconciled for retry)
                 │
                 └── crashCount >= 3 ──► REQUIRES_ATTENTION (quarantined poison pill)
```

### Audit Findings
- **Crash Count Tracking**: `crashCount` increments strictly on recovery from `PROCESSING`.
- **Attempt Isolation**: `attempts` is **not** incremented on worker termination. Network failures consume attempts; browser crashes consume `crashCount`.
- **Bounded Retries**: At `crashCount === 3`, the poison pill is safely isolated.
- **Evidence**: Verified in [`tests/security/storage-and-wal.test.ts:175-219`](file:///d:/Parth/Projects/CodeSync/tests/security/storage-and-wal.test.ts#L175-L219).

## 11. Recovery Idempotency

### Repeated Execution Analysis
When recovery runs multiple times consecutively (`reconcileWalAndOrphans()` followed immediately by `reconcileWalAndOrphans()`):
- **Pass 1**: Discovers uncommitted WAL entries, orphan payloads, or orphan metadata; reconstructs metadata and quarantines orphans; deletes processed WAL entries.
- **Pass 2**:
  - `getAllWalEntries()` returns `[]` -> 0 actions.
  - `getAllPayloadKeys()` matches existing metadata -> 0 actions.
  - All non-terminal metadata has valid payloads -> 0 actions.
  - Returns `reconciledWalCount: 0, recoveredOrphanPayloads: 0, quarantinedOrphanMetadata: 0`.

### Recovery Operation Idempotency Classification

| Operation | Idempotency Classification | Side Effects on Re-run |
|---|---|---|
| **WAL Cleanup (Boundary B/H/I)** | **IDEMPOTENT** | No-op (entry already deleted) |
| **Metadata Reconstruction (Boundary C)** | **IDEMPOTENT** | Metadata already in `storage.local`; WAL already deleted |
| **Orphan Payload Quarantine (Boundary G)** | **IDEMPOTENT** | Payload key already in `knownPayloadIds`; no duplicates created |
| **Orphan Metadata Quarantine (Boundary F)** | **IDEMPOTENT** | Item already in `REQUIRES_ATTENTION`; skipped on subsequent pass |
| **Interrupted PROCESSING Reconciliation** | **EVENTUALLY IDEMPOTENT** | If item is in `PROCESSING`, transitions to `PENDING` or `REQUIRES_ATTENTION`. Once in `PENDING`, subsequent recovery passes do not touch it or increment `crashCount`. |

Evidence: Explicitly proven in [`tests/security/wal-crash-boundaries.test.ts:321-347`](file:///d:/Parth/Projects/CodeSync/tests/security/wal-crash-boundaries.test.ts#L321-L347) (Boundaries J & K).

## 12. Recovery Ordering

The execution sequence inside `QueueManager.drainQueue()` is strictly ordered:

```
1. CONCURRENCY LOCK ACQUIRED (Web Lock + Persistent Lease + Fencing Token N)
       │
       ▼
2. RECONCILE WAL & ORPHANS (reconcileWalAndOrphans)
   - Prune uncommitted WAL
   - Reconstruct metadata from WAL + Payload
   - Quarantine orphan payloads (REQUIRES_ATTENTION)
   - Quarantine orphan metadata (REQUIRES_ATTENTION)
       │
       ▼
3. RECONCILE INTERRUPTED ITEMS (reconcileInterruptedItems)
   - Items in PROCESSING -> increment crashCount
   - If crashCount >= 3 -> REQUIRES_ATTENTION (Poison Pill)
   - If crashCount < 3 -> PENDING
       │
       ▼
4. BATCH PROCESSING LOOP
   - Check rate-limit reset deadlines
   - Select candidate (claimNextItem)
   - Validate Fencing Token
   - Execute GitHub Sync Handler
   - Finalize Item (COMPLETED / FAILED / SKIPPED)
       │
       ▼
5. PURGE COMPLETED / RELEASE LEASE
```

### Ordering Invariant
Reconciliation of durable state is **100% complete** before candidate selection (`claimNextItem()`) begins. An un-reconciled or partially recovered item can never be claimed or dispatched to GitHub.

## 13. Recovery + Lease/Fencing

The recovery phase runs strictly under the authority of `QueueConcurrencyManager.runExclusively()`.

### Dual-Tier Authority
1. **Tier 1 (Browser Process Level)**: Web Locks API (`navigator.locks.request("codesync:queue:drain:lock")`).
2. **Tier 2 (Durable Persistent Lease & Fencing)**: Stored in `codesync:queue:lease` in `browser.storage.local`.

### Authority at Mutation Boundaries
- **Start Authority**: Worker acquires persistent lease, incrementing `fencingToken` (e.g. from $N$ to $N+1$).
- **Claim Authority**: When `claimNextItem()` transitions an item from `PENDING` to `PROCESSING`, it binds the active `fencingToken` directly into `item.fencingToken`.
- **Mutation Authority**: Before committing final status in `finalizeItem()`, `validateFencingToken()` verifies that the worker's token matches the current durable lease record. If a newer worker superseded the lease during a suspension, `StaleLeaseError` is thrown, and the write is aborted fail-closed.
- Evidence: Verified in [`tests/security/crash-boundary-recovery.test.ts:422-514`](file:///d:/Parth/Projects/CodeSync/tests/security/crash-boundary-recovery.test.ts#L422-L514) (CRASH-INT-05) and [`tests/security/persistent-lease-fencing.test.ts:38-150`](file:///d:/Parth/Projects/CodeSync/tests/security/persistent-lease-fencing.test.ts#L38-L150) (FENCE-INT-01–04).

## 14. Recovery + WAL Crash Races

### Scenario Analysis: Crash During Recovery
Suppose **Worker A** begins recovery, reconstructs metadata for an item into `storage.local`, but crashes **before** deleting the WAL entry in IndexedDB:
1. **Durable State at Crash**:
   - `storage.local`: contains reconstructed item (`state: PENDING`, `id: item_1`).
   - IndexedDB `wal_logs`: contains WAL entry (`entityId: item_1`, `phase: INTENT`).
   - IndexedDB `payloads`: contains payload `payload:item_1`.
2. **Fresh Worker B Startup**:
   - Worker B acquires lease and runs `reconcileWalAndOrphans()`.
   - Reads `walEntries` (finds `item_1`).
   - Reads `metadataList` (finds `item_1` already present in `storage.local`).
   - Condition matches: `existingMeta !== undefined`.
   - Action: `await this.payloadStorage.deleteWalEntry(wal.id);`.
   - Summary: Residual WAL entry is pruned; metadata is **not** duplicated.
3. **Conclusion**: Safe and deterministic. No duplicate records, no data corruption.

## 15. Recovery + Retry / Rate Limits

### Interaction with Durable Retry State
- **Rate-Limited Items (HTTP 429 / Secondary Rate Limits)**:
  - When GitHub responds with HTTP 429, `QueueGitHubHandler` sets `item.state = QueueState.FAILED`, `item.nextRetryAt = resetTimestamp`, `item.lastError = { code: ErrorCode.GITHUB_RATE_LIMITED, ... }`, and increments `item.attempts`.
  - This state is persisted durably to `codesync:queue:metadata`.
- **Worker Crash During Rate Limit**:
  - If the service worker terminates while an item is waiting for `nextRetryAt`:
  - When fresh Worker B boots and runs startup drain before the deadline, `claimNextItem()` filters out items where `item.nextRetryAt > Date.now()`.
  - Zero network calls are dispatched.
  - When the deadline expires (via alarm or subsequent event), the item is claimed and retried cleanly.
- **Evidence**: Verified in [`tests/security/crash-boundary-recovery.test.ts:326-417`](file:///d:/Parth/Projects/CodeSync/tests/security/crash-boundary-recovery.test.ts#L326-L417) (CRASH-INT-04).

## 18. Payload Lifecycle

```
[Capture / Submission]
         │
         ▼
[PayloadStorage.putPayload()] ──► Stored in IndexedDB 'payloads'
         │
         ▼
[Referenced by QueueItemMetadata.payloadId]
         │
         ▼
[Active Processing / GitHub Sync] ──► Payload read via getPayload()
         │
         ▼
[Terminal State: COMPLETED / SKIPPED]
         │
         ▼
[QueueManager.purgeCompleted()] ──► Deletes metadata + payload in IndexedDB
```

### Lifecycle Guarantees
1. **Retention During Active States**: Payloads are never deleted while an item is in `PENDING`, `PROCESSING`, `FAILED`, or `REQUIRES_ATTENTION`.
2. **Orphan Payloads**: Payloads without metadata are never deleted; they are quarantined into `REQUIRES_ATTENTION`.
3. **Purge Protection**: `purgeCompleted()` deletes the payload only after the item has reached terminal `COMPLETED` or `SKIPPED` and history has been recorded.
4. **Stale Worker Defense**: A stale worker cannot delete an active payload because deletion occurs only under active lease authority.

## 19. WAL Cleanup

### Audit Points
- **When Removed**: During normal enqueue, `deleteWalEntry` is executed immediately after `COMMITTED` phase is written. During recovery, uncommitted or residual WAL entries are removed after reconciliation decisions are persisted.
- **Timing Relative to Durability**: WAL is **never deleted** before both payload and metadata durability are established.
- **Idempotency**: Deleting a non-existent WAL entry in IndexedDB is a safe no-op.
- **Stale Worker Defense**: Even if an old worker attempts to delete a WAL entry late, the entry has either already been deleted or its corresponding metadata has already been safely committed.

## 20. Corruption / Tampering Handling

The repository enforces a strict **fail-closed posture** for corrupted or hostile durable states:

1. **Hostile / Malformed Metadata Array**:
   - In [`src/shared/storage/local.ts:89-106`](file:///d:/Parth/Projects/CodeSync/src/shared/storage/local.ts#L89-L106): If `codesync:queue:metadata` contains non-array data, it is isolated to `codesync:corrupted` via `isolateCorrupted()`.
   - Returns a safe empty array `[]` to prevent extension crash loops.
2. **Tampered Queue Item Fields**:
   - If an item in `storage.local` is modified (e.g. `validatedBy` missing or invalid origin/UUID), `claimNextItem()` / `validateQueueItem()` fails closed.
   - Transitions item to `QueueState.REQUIRES_ATTENTION` with `ErrorCode.INVARIANT_VIOLATION`.
   - Dispatch to GitHub is blocked (0 network calls).
   - Evidence: Verified in [`tests/security/crash-boundary-recovery.test.ts:519-554`](file:///d:/Parth/Projects/CodeSync/tests/security/crash-boundary-recovery.test.ts#L519-L554) (CRASH-INT-06-SEC).

## 21. Duplicate / Multiple-WAL Handling

### Content Identity vs Submission Identity
The repository strictly respects:
$$\text{Submission Identity} \neq \text{Content Identity}$$

- Multiple submissions with identical source code have distinct `submissionId` values and distinct `entityId` UUIDs.
- In `reconcileWalAndOrphans()`:
  - WAL matching is keyed on `wal.entityId`.
  - Two distinct submissions with identical `contentHash` will have distinct WAL entries (`opId_1` for `sub_1`, `opId_2` for `sub_2`).
  - Recovery does not collapse them into a single record.
- In `enqueueSubmission()`:
  - Deduplication prevents queuing the identical problem if an active submission is already in flight. Once terminal, new submissions are accepted.

## 22. Recovery History

### Sync History Guarantees
- History entries are appended to `codesync:history` only upon confirmed completion (`finalizeItem()`).
- Recovery itself does **not** generate speculative history entries.
- If an item is recovered into `REQUIRES_ATTENTION`, history is updated with status `error` or `quarantined`.
- If an item was confirmed on GitHub by Worker A and reconciled as `SKIPPED` by Worker B, exactly **one** history entry is written (`status: "skipped"`).
- Duplicate history entries are rejected via deterministic timestamp and content hash correlation.

## 23. Queue State Machine

### Effective Recovery State Machine

```
              ┌─────────────── [ Enqueue ] ──────────────┐
              ▼                                          ▼
         [ PENDING ]                               [ REQUIRES_ATTENTION ]
              │                                      ▲  ▲  ▲
     claimNextItem()                                 │  │  │
              ▼                                      │  │  │
        [ PROCESSING ] ──(crashCount >= 3)───────────┤  │  │
              │                                      │  │  │
     Worker Crash (< 3) ──► Reconciled to PENDING    │  │  │
              │                                      │  │  │
     Handler Outcome:                                │  │  │
              ├── 200 OK ──────► [ COMPLETED ]       │  │  │
              ├── 409 Identical ► [ SKIPPED ]        │  │  │
              ├── Rate Limit ──► [ FAILED ]          │  │  │
              ├── Missing Payload ───────────────────┘  │  │
              └── Orphan Payload Recovered ─────────────┘  │
                                                           │
        Tampered State / Invariant Violation ──────────────┘
```

### State Transitions Table

| Initial State | Event / Trigger | Authority | Resulting State | Retry Implications | Idempotent? |
|---|---|---|---|---|---|
| `UNQUEUED` | `enqueueSubmission` | Client Message | `PENDING` | `attempts: 0` | Yes |
| `PENDING` | `claimNextItem` | Fencing Token $N$ | `PROCESSING` | `attempts` unchanged | Yes |
| `PROCESSING` | Worker Crash (1st/2nd) | Recovery Startup | `PENDING` | `crashCount++`, `attempts` unchanged | Yes |
| `PROCESSING` | Worker Crash (3rd) | Recovery Startup | `REQUIRES_ATTENTION` | Poison pill quarantined | Yes |
| `PROCESSING` | Success (200 / 201) | Fencing Token $N$ | `COMPLETED` | Terminal | Yes |
| `PROCESSING` | Remote Identical | Fencing Token $N$ | `SKIPPED` | Terminal | Yes |
| `PROCESSING` | Transient Error | Fencing Token $N$ | `FAILED` | `attempts++`, backoff set | Yes |
| Any Active | Missing Payload | Recovery Startup | `REQUIRES_ATTENTION` | `PAYLOAD_NOT_FOUND`, no retry | Yes |
| Orphan Payload | No Metadata | Recovery Startup | `REQUIRES_ATTENTION` | `RECOVERED_ORPHAN_PAYLOAD` | Yes |
| Any | Storage Tampering | Fencing Token $N$ | `REQUIRES_ATTENTION` | `INVARIANT_VIOLATION`, no retry | Yes |

## 28. Security Invariants

1. **`UNKNOWN DURABLE STATE != SUCCESS`**: Verified. Unparseable metadata is isolated to `codesync:corrupted`; missing payloads transition to `REQUIRES_ATTENTION`.
2. **`UNKNOWN REMOTE WRITE != SAFE TO PUT AGAIN`**: Verified. Pre-flight `GET` inspects GitHub state before issuing `PUT`.
3. **`STALE WORKER != RECOVERY AUTHORITY`**: Verified. Persistent lease and fencing token validation reject mutations from superseded workers.
4. **`ORPHAN PAYLOAD != AUTOMATICALLY TRUSTED SUBMISSION`**: Verified. Orphan payloads are quarantined into `REQUIRES_ATTENTION` with `status: "RECOVERED_ORPHAN_PAYLOAD"` and never sent to GitHub.
5. **`ORPHAN METADATA != VALID SOURCE CONTENT`**: Verified. Missing payload triggers `ErrorCode.PAYLOAD_NOT_FOUND` and blocks synchronization.
6. **`SUBMISSION IDENTITY != CONTENT IDENTITY`**: Verified. Distinct submissions with matching content hashes retain distinct queue identities.
7. **`WEB LOCK != DURABLE OWNERSHIP`**: Verified. Persistent lease in `browser.storage.local` provides cross-worker durable ownership beyond ephemeral in-memory Web Locks.
8. **`LEASE START AUTHORITY != MUTATION-COMPLETION AUTHORITY`**: Verified. Fencing tokens are re-validated before finalizing writes.
9. **`RECOVERY != PERMISSION TO GUESS`**: Verified. Ambiguous or incomplete states fail closed into `REQUIRES_ATTENTION`.

## 30. Design Gaps

1. **Direct Invocation of Recovery Outside Concurrency Guard**:
   - `reconcileWalAndOrphans()` and `reconcileInterruptedItems()` are public methods on `QueueManager`.
   - In production, they are only invoked inside `drainQueue()`, which wraps them in `this.concurrency.runExclusively()`.
   - *Design Gap*: If a developer or external caller invokes `reconcileWalAndOrphans()` directly on `queueManager` without acquiring the persistent lease, recovery would execute without fencing validation.
   - *Impact*: Low in current architecture because `drainQueue` is the sole entry point, but encapsulation could be strengthened in future refactoring.
