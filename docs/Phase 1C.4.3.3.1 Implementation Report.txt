- **`FAIL-MAT-06`**: **PASSED** (Pre-flight GET 5xx classifies as retryable failure without uncertain-write reconciliation; schedules durable backoff; retries and completes on subsequent drain).
- **`FAIL-MAT-01`**: **FAILED (Production Defect Exposed)**: In [`src/shared/auth/token-lifecycle.ts:158,178-188`](file:///d:/Parth/Projects/CodeSync/src/shared/auth/token-lifecycle.ts#L158-L188), when `getValidAccessToken({ forceRefresh: true })` is invoked following an initial HTTP 401 Unauthorized response from GitHub, `executeCoordinatedRefresh` checks `timeRemaining > this.preFlightBufferMs && currentAuth.refreshState === "IDLE"`. Because `forceRefresh` intent is discarded, `executeCoordinatedRefresh` falsely assumes another concurrent worker already refreshed the token, returns the identical 401-rejected token without contacting the OAuth refresh endpoint, and causes the retried operation to immediately fail with a second terminal 401.
- **`FAIL-MAT-02`**: **FAILED (Production Defect Exposed)**: Due to the exact same defect in [`src/shared/auth/token-lifecycle.ts:178-188`](file:///d:/Parth/Projects/CodeSync/src/shared/auth/token-lifecycle.ts#L178-L188), when GitHub returns HTTP 401, `executeCoordinatedRefresh` bypasses outbound token refresh completely for any locally unexpired token TTL. Consequently, the OAuth endpoint is never contacted, the revoked refresh token (`bad_refresh_token`) is never evaluated, the durable auth state never transitions to `"reauth_required"`, and the queue item fails with `GITHUB_UNAUTHORIZED` instead of discovering the revoked credential.

In accordance with the **Strict Stop-on-Production-Defect Policy**, execution was halted immediately upon establishing the defect, zero production fixes were applied, and evidence has been preserved.

## 4. Formal Defect Report: DEFECT-1C.4.3.3.1-01

### 1. Exact Failing Tests
- `FAIL-MAT-01`: 401 triggers coordinated token refresh and succeeds on single retry
- `FAIL-MAT-02`: 401 with revoked/failing refresh token fails closed into quarantine

### 2. Exact Production File & Functions Involved
- **File**: [`src/shared/auth/token-lifecycle.ts`](file:///d:/Parth/Projects/CodeSync/src/shared/auth/token-lifecycle.ts)
- **Functions**:
  - `getValidAccessToken(options?: { forceRefresh?: boolean; workerId?: string })` (lines 113–160)
  - `executeCoordinatedRefresh(workerIdParam?: string)` (lines 164–270)

### 3. Observed Behavior
When `getValidAccessToken({ forceRefresh: true })` is called for an authentication credential whose locally persisted `tokenExpiresAt` is in the future (`timeRemaining > this.preFlightBufferMs`):
1. `getValidAccessToken` checks `!options?.forceRefresh` on line 149 and bypasses the fast-path check.
2. `getValidAccessToken` invokes `this.executeCoordinatedRefresh(options?.workerId)` on line 158. Notice that `forceRefresh: true` is **not** passed as an argument.
3. Inside `executeCoordinatedRefresh`, under the Web Lock on lines 178–188:
   ```ts
   const timeRemaining = currentAuth.tokenExpiresAt - now;
   if (
     currentAuth.status === "authenticated" &&
     timeRemaining > this.preFlightBufferMs &&
     currentAuth.refreshState === "IDLE"
   ) {
     return {
       alreadyRefreshed: true as const,
       token: currentAuth.accessToken,
     };
   }
   ```
4. `executeCoordinatedRefresh` checks whether `timeRemaining > this.preFlightBufferMs`. Because `tokenExpiresAt` is still in the future, this condition evaluates to `true`.
5. `executeCoordinatedRefresh` concludes that another concurrent worker already refreshed the token (`alreadyRefreshed: true`).
6. It returns the existing, un-refreshed `currentAuth.accessToken`.
7. Outbound HTTP POST to `GITHUB_OAUTH_TOKEN_URL` is never dispatched (`fetchFn` call count is 0).
8. `GitHubApiClient.request()` receives the identical 401-rejected token, executes its single retry with the same token, receives another 401, and fails terminally into quarantine.

### 4. Expected Behavior
When `forceRefresh: true` is explicitly passed to `getValidAccessToken` (which occurs when GitHub REST API returns HTTP 401 Unauthorized for an active request):
1. `executeCoordinatedRefresh` must receive the `forceRefresh` intent (or track the initial generation of the caller).
2. It must **not** assume the token was already refreshed simply because `timeRemaining > this.preFlightBufferMs`. (A token may be invalidated or revoked server-side by GitHub at any time while still possessing unelapsed local TTL).
3. It must only consider the token `alreadyRefreshed` if a concurrent worker has actually committed a newer credential generation (`currentAuth.refreshGeneration > callerGeneration`).
4. It must claim the persistent refresh lease, transition `refreshState` to `"REFRESHING"`, and dispatch the POST request to the OAuth refresh endpoint.

### 5. Why This Is a Real Production Defect
In GitHub's authorization architecture, access tokens can be invalidated, revoked, or expired server-side at any time prior to their nominal expiration (e.g., user revokes application in GitHub settings, admin security policy changes, token rotation on another device). When this happens, CodeSync's durable storage still has `tokenExpiresAt` set to a future timestamp.

`GitHubApiClient.request()` correctly detects this condition via HTTP 401 and calls `this.getAccessToken(true)` to trigger the coordinated forced refresh. However, because `DurableTokenLifecycleManager` unconditionally checks `timeRemaining > preFlightBufferMs` inside `executeCoordinatedRefresh`, it completely short-circuits the refresh mechanism and returns the dead token.

This permanently disables 401 token refresh recovery in production for all tokens revoked prior to local TTL expiration.

### 6. Reproduction Path
1. Seed `codesync:auth` storage with `status: "authenticated"`, `tokenExpiresAt: Date.now() + 3600_000`, `refreshState: "IDLE"`, `refreshGeneration: 1`.
2. Configure mock GitHub API server to return HTTP 401 Bad credentials for the initial request.
3. Enqueue a submission item and call `queueDrainer.drain("submission_event")`.
4. Observe that `executeCoordinatedRefresh` returns `{ alreadyRefreshed: true }` without invoking `fetchFn`.
5. Observe that `GitHubApiClient.request()` retries with the identical token, receives a second 401, and the queue item transitions to `requires_attention`.

### 7. Harness / Helper Contribution Analysis
The failure was not caused by any test helper or mock deficiency:
- The test provided a valid `lifecycleManagerFactory` returning a real production `DurableTokenLifecycleManager`.
- The mock OAuth token URL handler was never invoked because execution was halted inside `executeCoordinatedRefresh` before dispatch.
- Zero production code was modified in this phase.
