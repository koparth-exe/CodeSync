### A. Executive Summary

Phase 1C.4.1 establishes the authoritative integration boundary connecting the Phase 1C.3 platform submission extraction pipeline to the Phase 1B.1 durable Write-Ahead Log (WAL) backed queue within the extension service worker.

Prior to this phase:
- Platform adapters detected and parsed submissions into a canonical candidate structure.
- Message validation rejected spoofed or malformed envelopes, but stopped short of durable persistence.
- The durable WAL queue could enqueue submissions, but lacked immutable target snapshotting, active duplicate enqueue suppression, and end-to-end integration with the service worker message dispatcher.

In Phase 1C.4.1, the complete pipeline was implemented: incoming submission messages from content scripts are verified against runtime sender context and platform origins, validated deterministically against canonical submission invariants, normalized for deterministic UTF-8/LF line endings, hashed via SHA-256 for content identity, paired with a frozen target configuration snapshot, and committed to the hybrid persistent queue strictly through the intent-first Write-Ahead Log.

### C. Architecture

The data flow strictly enforces the unidirectional trust and validation pipeline:

```
WEBPAGE (Untrusted DOM / JS Execution)
  ↓
CONTENT SCRIPT (Untrusted Execution Context)
  ↓
PLATFORM ADAPTER (Extracts Candidate, assigns source: 'CONTENT_SCRIPT_EXTRACTED')
  ↓
CANONICAL SUBMISSION CANDIDATE (Typed Extension Message: SUBMISSION_DETECTED)
  ↓
SERVICE WORKER [AUTHORITATIVE TRUST BOUNDARY]
  ├── Runtime Sender Authorization (Validates sender.id === extension.id, tab URL matches platform)
  ├── Invariant & Provenance Validation (Rejects spoofed 'AUTHORITATIVE_SERVICE_WORKER')
  ├── Invariant Validation (Status MUST be 'ACCEPTED', payload <= 500 KB)
  ├── Canonical Source Normalization (normalizeSourceCode: CRLF -> LF, trims trailing space, adds final LF)
  ├── Content Identity (Deterministic SHA-256 over normalized source)
  ├── Target Snapshot Capture (Freezes owner/repo, branch via Safe Branch Grammar, baseFolder via 5-Pillars, duplicatePolicy)
  └── Queue Insertion via Durable WAL
        ├── Duplicate Check (Returns existing item if ID or platform+problem+hash is already PENDING/PROCESSING)
        ├── 1. Create WAL INTENT (IDB: wal_entries)
        ├── 2. Persist WAL INTENT (Durably committed)
        ├── 3. Persist Source Payload (IDB: payload_records)
        ├── 4. Persist Queue Metadata (browser.storage.local: codesync:queue_items)
        └── 5. Mark WAL INTENT Status → COMPLETED (IDB: wal_entries)
```

---

### D. WAL Behavior

Persistence ordering follows the non-negotiable intent-first invariant of Phase 1B.1:

1. **Active Duplicate Check**: Verifies existing queue items. If an identical submission is already in `PENDING` or `PROCESSING` state, returns that item idempotently without touching the WAL.
2. **Intent Generation**: Constructs a WAL entry (`operation: "ENQUEUE"`, `status: "PENDING"`) containing the complete snapshot (`metadata`, `targetSnapshot`, `submissionId`, `sourceProvenance`, `payloadSize`, `contentHash`).
3. **Intent Persistence**: Calls [`idb.putWalEntry`](file:///d:/Parth/Projects/CodeSync/src/shared/storage/indexeddb.ts). The WAL entry is durably written to IndexedDB *before any data stores are modified*.
4. **Payload Persistence**: Calls [`idb.putPayload`](file:///d:/Parth/Projects/CodeSync/src/shared/storage/indexeddb.ts). The normalized source payload is written to the IndexedDB `payload_records` store.
5. **Metadata Persistence**: Reads the active queue index and metadata from `browser.storage.local`, appends the new queue item (with its immutable `targetSnapshot`), and commits it.
6. **Intent Completion**: Updates the WAL entry status to `COMPLETED` in IndexedDB.

At no point does code write the payload or metadata before the WAL intent is persisted, and at no point are `browser.storage.local` and IndexedDB assumed to be cross-store atomic.

---

### E. Queue Behavior

Upon successful completion of the boundary, a queue item is created with the following properties:
- **`id`**: Deterministic UUIDv4 generated during intent formulation.
- **`submissionId`**: Platform-specific submission ID from the candidate.
- **`platform`**: Platform identifier (e.g. `leetcode`).
- **`problemSlug`**: Platform problem slug (e.g. `two-sum`).
- **`language`**: Submission language (e.g. `typescript`).
- **`status`**: `"PENDING"`.
- **`attemptCount`**: `0`.
- **`maxAttempts`**: Configured default (e.g. `3`).
- **`createdAt` / `updatedAt`**: ISO timestamp.
- **`payloadRef`**: Key reference to the durable payload in IndexedDB (`queue_item_{id}`).
- **`contentHash`**: SHA-256 hex digest of the normalized source code.
- **`sourceProvenance`**: Authoritative provenance stamp assigned by the service worker (`AUTHORITATIVE_SERVICE_WORKER`).
- **`targetSnapshot`**: Immutable target configuration containing:
  - `repository`: e.g. `owner/repo`
  - `branch`: e.g. `main`
  - `baseFolder`: e.g. `leetcode`
  - `duplicatePolicy`: e.g. `REPLACE_IF_DIFFERENT`

### F. Security

1. **Untrusted Content Script / DOM**:
   - The webpage and content script have no ability to write directly to IndexedDB or `browser.storage.local`.
   - Content scripts cannot supply authoritative source provenance. If a message contains `source: "AUTHORITATIVE_SERVICE_WORKER"`, the service worker rejects it immediately (`PROVENANCE_SPOOF_REJECTED`).
   - Content scripts cannot specify target repositories, branches, file paths, or duplicate policies. All target parameters are loaded and validated strictly by the service worker from extension storage.
2. **Runtime Sender Authorization**:
   - `runtimeSender.id` must strictly match `browser.runtime.id`.
   - `runtimeSender.url` must originate from an authorized platform domain matching the candidate platform (e.g., `leetcode.com` or `leetcode.cn` for `leetcode`).
3. **Deterministic Canonical Invariants**:
   - Submissions with status other than `"ACCEPTED"` are rejected prior to queue insertion.
   - Payloads exceeding 500 KB (512,000 bytes) are rejected with `PAYLOAD_OVERSIZED`.
4. **Source Code Privacy**:
   - Source code is strictly placed into the IndexedDB payload store.
   - Raw source code is never placed in `browser.storage.local`, error messages, logs, or diagnostics.
5. **No Credential Exposure**:
   - Access tokens, refresh tokens, and installation tokens are excluded from queue metadata, WAL snapshots, and payloads.

| **C. | **D. ### H. Idempotency & Duplicate Enqueue Protection

Duplicate submission events (e.g. network retries, repeated DOM mutations from SPAs, or duplicate content script messaging) are handled idempotently:
1. When a submission candidate is validated, the service worker checks active queue items in `PENDING` or `PROCESSING` state.
2. If an item matches by `id`, `submissionId`, or `(platform, problemSlug, contentHash)`, the existing queue item is returned immediately with `status: "EXISTING_ITEM"`.
3. No duplicate WAL intent is generated, no duplicate payload is written, and no redundant queue metadata is appended.

---

### I. Immutable Target Snapshot

The target repository, branch, base folder, and duplicate policy are resolved from extension local storage at enqueue time and frozen inside [`TargetSnapshot`](file:///d:/Parth/Projects/CodeSync/src/shared/storage/types.ts#L33-L44):
- Target branch is validated against the Safe Branch Grammar.
- Base folder is validated against the 5-Pillar Path Defense (blocking absolute paths, `..`, control characters, null bytes).
- The resolved `TargetSnapshot` is stored in the WAL intent and embedded directly into [`QueueItemMetadata`](file:///d:/Parth/Projects/CodeSync/src/shared/storage/types.ts#L46-L71).
- **Subsequent user configuration changes** (e.g., changing `targetRepository` from `org/repo-A` to `org/repo-B` or `branch` from `main` to `develop`) **do not alter already-enqueued items**. Tests confirm the persisted queue item retains its original target snapshot.
