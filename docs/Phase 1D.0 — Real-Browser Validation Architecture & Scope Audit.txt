# PHASE-1D.0-REAL-BROWSER-VALIDATION-AUDIT.md
# Phase 1D.0 — Real-Browser Validation Architecture & Scope Audit

---

## 1. Executive Summary

CodeSync has successfully completed the entire Phase 1C integration track (Phases 1C.1 through 1C.4.3.7). The current repository baseline possesses a robust, deterministic, and crash-resilient architecture validated by **508 passing tests across 42 test files with zero failures and zero skipped tests**.

However, as formally established in Phase 1C.4.3.7, the existing test suite executes within a Node.js-based virtualized harness (`fake-browser`, `fake-indexeddb`, and simulated mock environments). While this proves mathematical and architectural correctness, it leaves an **evidence limitation**: the extension's behavior has not yet been demonstrated inside real, physical Chromium and Gecko browser engines.

This audit establishes the rigorous technical scope, boundaries, test cases, and automation strategy for real-browser runtime validation. It identifies exactly which behaviors require physical browser execution, which behaviors remain adequately proven by simulation, and outlines a targeted, zero-production-risk roadmap for **Phase 1D.1**.

**Audit Verdict**: `APPROVED WITH TARGETED EVIDENCE GAPS` (No confirmed production defects; targeted real-browser runtime evidence gaps identified and scoped).

## 2. Audit Scope

### In-Scope
- Exact runtime execution paths across physical **Chromium MV3** and **Firefox MV3** engines.
- Native extension installation, manifest parsing, and permission ingestion.
- Background execution contexts: Chromium ephemeral Service Worker vs. Firefox Background Event Page.
- Native browser storage drivers (`chrome.storage.local`, `browser.storage.local`, LevelDB/SQLite backed).

- Real Web Locks API (`navigator.locks`) and multi-process persistent lease fencing.
- Extension IPC messaging (`browser.runtime.sendMessage` / `onMessage`, port keepalive, asynchronous response delivery).
- Real browser network boundaries (Service Worker `fetch`, host permissions, CORS bypass, request timeouts).
- Real Content Security Policy (CSP) enforcement and Isolated World DOM boundary security.

- Adding Playwright, Puppeteer, or automation frameworks during this phase.
- Implementing test cases or fixing hypothetical issues.
- Performing live writes to external user GitHub repositories or using live GitHub accounts.

## 4. Browser Architecture Matrix

| Capability / Subsystem | Chromium MV3 Target | Firefox MV3 Target | Architectural Difference |
|---|---|---|---|
| **Background Model** | Service Worker (`background.js`) | Non-persistent Background Event Page (`scripts: ["background.js"]`) | **DIFFERENT**: Chrome terminates V8 isolate aggressively on idle (30s); Firefox suspends DOM-capable event page. |
| **Messaging Channel** | `chrome.runtime.onMessage` with callback `sendResponse` & `return true;` | `browser.runtime.onMessage` supporting Promise resolution or `sendResponse` | **SAME** in CodeSync: CodeSync uses callback `sendResponse` with synchronous `return true;` to maintain parity. |
| **Storage API** | `chrome.storage.local` (callback with `chrome.runtime.lastError`) | `browser.storage.local` (native Promise-returning) | **DIFFERENT**: Abstraction in `WebExtensionStorageDriver` normalizes both to typed `StorageError`. |
| **IndexedDB Engine** | Chromium LevelDB-backed IndexedDB in Service Worker | Gecko SQLite-backed IndexedDB in Event Page | **SAME** API standard; different low-level locking and transaction auto-commit timing. |
| **Concurrency (Tier 1)** | Native `navigator.locks` | Native `navigator.locks` | **SAME**: Both supported natively in declared baseline (Chrome 92+, Firefox 128+). |
| **Concurrency (Tier 2)** | Persistent lease in `codesync:queue:lease` with monotonic fencing | Persistent lease in `codesync:queue:lease` with monotonic fencing | **SAME**: Universal storage-backed fallback. |
| **Periodic Wakeup** | `chrome.alarms` wakes terminated Service Worker | `browser.alarms` wakes suspended Event Page | **SAME** minimum interval (1 minute) and wake behavior. |
| **Content Scripts** | Injected into Isolated World at `document_idle` | Injected into Content Script Sandbox at `document_idle` | **SAME** boundary invariants; isolated JS execution context sharing DOM. |

## 5. Runtime Boundary Analysis

Real-browser runtime execution exercises physical boundaries that virtualized Node.js harnesses cannot replicate:

```
[ Webpage Execution Context (Untrusted) ]
   │
   ├── DOM Boundary (Shared Elements) ──┐
   │                                    ▼
[ Content Script Isolated World ] ──▶ [ Extension Messaging Port ]
                                                │
                                                ▼ (IPC via Browser Process)
                                      [ Extension Service Worker / Event Page ]
                                                │
                                 ┌──────────────┴──────────────┐
                                 ▼                             ▼
                     [ Storage Driver (LevelDB) ]   [ Fetch Network Context ]
                                 │                             │
                                 ▼                             ▼
                     [ Persistent Storage / IDB ]   [ GitHub API (Host Perms) ]
```

1. **The Native Isolated World Boundary**:
   - In JSDOM, `window` and prototypes are shared. In a real browser, the webpage and content script have independent `Object`, `Array`, and `Function` prototypes. Real-browser validation proves that hostile webpage prototype poisoning cannot compromise CodeSync content scripts.
2. **Synchronous Cold Wakeup vs. Asynchronous Dispatch**:
   - In Chromium MV3, when an alarm or runtime message wakes a terminated service worker, the browser loads `background.js` from disk. If event listeners (`onMessage`, `onAlarm`) are not attached synchronously during the initial top-level turn, the dispatch is lost.
3. **Storage Latency & Concurrent Page/Worker Access**:
   - A real browser writes `chrome.storage.local` to disk asynchronously. Real-browser tests ensure that concurrent storage reads/writes between popup UI and background workers never cause write starvation or torn reads.

## 6. Chrome Findings

1. **Manifest Parsing & V3 Service Worker Registration**:
   - WXT compiles Chrome MV3 with `"background": { "service_worker": "background.js" }`.
   - Verified that no invalid Manifest V2 keys (e.g., `browser_action`, `background.scripts`) are present.
   - `minimum_chrome_version: "92"` correctly blocks installation on obsolete Chromium engines lacking `crypto.randomUUID()`.
2. **Aggressive Idle Termination (30-second Timer)**:
   - Chromium terminates service workers after 30 seconds of inactivity.
   - CodeSync does **not** rely on artificial keepalives or WebSocket hacks. Its state machine is built for cold restart:
     - All queue items, leases, and retry timestamps reside in `storage.local`.
     - All source payloads and WAL logs reside in `IndexedDB`.
   - Real-browser validation must verify that when Chromium stops the worker mid-flight, a subsequent wake event re-reads durable state, increments `crashCount`, and resumes cleanly.

---

## 7. Firefox Findings

1. **Event Page Execution Model**:
   - WXT compiles Firefox MV3 with `"background": { "scripts": ["background.js"] }`.
   - Firefox MV3 currently uses non-persistent background event pages rather than service workers. This grants background scripts full DOM and standard Web Worker/Window-like API access.
   - Real-browser validation must verify that `background.js` executes reliably in the Gecko event page without assuming service-worker-specific global limitations.
2. **Gecko Native Promise Handling**:
   - In Firefox, `browser.*` APIs natively return Promises. CodeSync's `WebExtensionStorageDriver` uses standard callbacks with `chrome.*` fallbacks. Real Gecko validation confirms that error rejections propagate into typed `StorageError` instances with `failClosed: true`.
3. **Extension ID and Min Version**:
   - Manifest declares `id: "codesync@extension.local"` and `strict_min_version: "128.0"`.
   - Temporary installation in Firefox (`about:debugging`) requires a valid ID; verified that this ID is present and valid.

## 8. Browser-Sensitive Behaviors

| Behavior | Sensitivity | Chromium Characteristic | Gecko Characteristic | Real-Browser Necessity |
|---|---|---|---|---|
| **Top-Level Listener Attachment** | **CRITICAL** | Worker is killed when idle; listeners must bind synchronously on evaluation. | Event page suspends; wakes on registered events. | **HIGH**: Proves wake-up events are never dropped. |
| **Port Keepalive (`return true;`)** | **CRITICAL** | Port closes immediately unless listener synchronously returns `true`. | Same, but also supports Promise return. | **HIGH**: Proves async `sendResponse` does not throw "message channel closed". |
| **Storage Error Propagation** | **HIGH** | Populates `chrome.runtime.lastError` in callback. | Rejects Promise or throws exception. | **MEDIUM**: Verified in `CB-INT-04`; physical test confirms native driver errors. |
| **IndexedDB Transaction Auto-Commit** | **HIGH** | LevelDB auto-commits if microtask queue drains without pending requests. | SQLite engine; slightly different commit timing. | **HIGH**: Proves transaction stays active across payload and WAL writes. |
| **Web Locks Cross-Process Mutex** | **MEDIUM** | Coordinated by Chromium Browser Process across renderers/workers. | Coordinated by Gecko parent process. | **MEDIUM**: Proves locks yield cleanly on worker termination. |
| **Host Permission Fetch Bypass** | **HIGH** | Extension service worker bypasses CORS for `host_permissions`. | Event page bypasses CORS for `host_permissions`. | **HIGH**: Proves real fetch to `api.github.com` is permitted without CORS blocks. |

## 9. Real-Browser vs. Simulation Boundary

### Can Remain Simulation/Unit/Integration Tested
- **Canonical Payload Normalization & Hashing**: `computeContentHash` string trimming and SHA-256 computation are 100% deterministic and mathematically identical across environments.
- **Path Security Grammar & Traversal Rules**: Bounded POSIX path validation (`validateAndSanitizePath`), DOS name rejection, and `.git`/`.github` blocks are pure logic rules completely validated in Node.js.
- **Queue State Transition Permutations**: The 5-state machine (`PENDING`, `PROCESSING`, `COMPLETED`, `FAILED`, `ATTENTION`) and duplicate hierarchy rules are verified across 508 unit tests.
- **GitHub REST API Payload Construction & Tree Generation**: Commit message formatting, branch reference construction, and base64 blob encoding.
- **Adversarial Token Revocation & 401 Force-Refresh CAS**: Monotonic `refreshGeneration` counter progression and single-object CAS logic.

### Requires Real Browser Execution
- **Physical Unpacked Installation & Manifest Ingestion**: Validating that real Chrome and Firefox binaries accept the manifest, compile CSP, and inject background scripts without runtime load errors.
- **Live Content Script Injection across SPA Navigations**: Verifying that the content script actually attaches to real coding platform pages (or simulated platform DOMs in real browser tabs) upon `popstate` and `MutationObserver` events.
- **Asynchronous IPC Message Port Lifetime**: Proving that `browser.runtime.sendMessage` from a live content script receives the asynchronous `sendResponse` from the background service worker without "message port closed before a response was received".
- **Service Worker Ephemeral Termination & Alarm Resuscitation**: Inducing worker termination in a real browser process and verifying that `chrome.alarms` wakes the worker and resumes interrupted queue items.
- **Live Extension Network Stack (`fetch` via Service Worker)**: Verifying that `fetch` requests originating inside the service worker with `host_permissions` successfully reach the remote endpoint without browser-level security blocks or CSP interference.

## 11. Proposed Browser Test Cases

The following **12 targeted real-browser tests** are proposed for **Phase 1D.1**:

### P0 Tests (Mandatory for Release Baseline)

#### `RB-INSTALL-01`: Chromium MV3 Unpacked Installation
- **Objective**: Verify Chrome loads the unpacked extension without manifest, permission, or CSP warnings.
- **Setup**: Launch Chromium with `--load-extension=.output/chrome-mv3`.
- **Action**: Inspect `chrome://extensions` and extension service worker registration.
- **Expected Result**: Extension ID generated; status "active"; 0 console errors during manifest ingestion.
- **Invariants**: `minimum_chrome_version: "92"`, permissions `["storage", "alarms"]`.

#### `RB-INSTALL-02`: Firefox MV3 Unpacked Installation
- **Objective**: Verify Firefox loads the unpacked extension via temporary add-on API.
- **Setup**: Launch Firefox with `.output/firefox-mv3` installed.
- **Action**: Query extension status via Marionette/web-ext.
- **Expected Result**: Extension registered with `codesync@extension.local`; background event page loads.
- **Invariants**: `strict_min_version: "128.0"`.

#### `RB-STARTUP-01`: Synchronous Background Initialization (Chrome)
- **Objective**: Verify that service worker initializes synchronously and attaches all required listeners before IPC dispatch.
- **Setup**: Chromium running with extension installed.
- **Action**: Query service worker registration state; inspect registered alarms via `chrome.alarms.getAll()`.
- **Expected Result**: Alarm `codesync:queue:drain` exists with `periodInMinutes: 1`; top-level `onMessage` listener active.
- **Invariants**: C-18 (Zero in-memory authoritative state required).

#### `RB-STARTUP-02`: Synchronous Background Initialization (Firefox)
- **Objective**: Verify that Firefox background event page registers alarms and listeners on startup.
- **Setup**: Firefox running with extension installed.
- **Action**: Query alarm state and event page status.
- **Expected Result**: Alarm registered; background listener ready.

#### `RB-MSG-01`: Content Script to Background Async IPC Parity
- **Objective**: Verify live `browser.runtime.sendMessage` keepalive (`return true;`) delivers typed response from service worker.
- **Setup**: Browser tab loaded with simulated platform page (`https://leetcode.com/problems/two-sum/`).
- **Action**: Content script dispatches `SUBMISSION_DETECTED` message; awaits Promise.
- **Expected Result**: Message validated; queue item created in `chrome.storage.local`; sender receives `{ success: true, queueItem }` without channel drop.
- **Invariants**: I-01, I-02, I-03 (Sender context derived from `sender.tab`).

#### `RB-PERSIST-01`: Physical Storage & IndexedDB Persistence Across Browser Restart
- **Objective**: Verify that queue items, payloads, and WAL entries survive physical browser restart.
- **Setup**: Seed item in `storage.local` and payload in `IndexedDB`.
- **Action**: Terminate browser process; relaunch browser with same profile; query storage.
- **Expected Result**: Data in `codesync:queue:metadata` and `codesync_db` completely identical; no data loss.
- **Invariants**: I-10, C-07 (WAL and Queue durability).

#### `RB-LIFECYCLE-01`: Service Worker Termination & Interrupted Recovery (Chrome)
- **Objective**: Verify that terminating a running service worker leaves queue state recoverable.
- **Setup**: Queue item marked `PROCESSING`.
- **Action**: Force terminate worker via CDP (`ServiceWorker.stopWorker`); trigger wake-up via alarm or message.
- **Expected Result**: On cold start, `reconcileInterruptedItems` resets item to `PENDING` and increments `crashCount` to 1.
- **Invariants**: C-09 (Interrupted processing is recoverable).

#### `RB-SECURITY-01`: Real DOM Isolation & CSP Enforcement
- **Objective**: Verify that hostile webpage scripts cannot invoke extension APIs or execute inline script in extension contexts.
- **Setup**: Webpage attempts to access `chrome.runtime.sendMessage` with extension ID; popup HTML loaded.
- **Action**: Inject malicious script in webpage DOM; inspect popup CSP.
- **Expected Result**: Webpage request rejected/inaccessible; inline script evaluation in extension page blocked by CSP.
- **Invariants**: `WEBPAGE != TRUSTED`, CSP `script-src 'self'`.

### P1 Tests (Mandatory for Release Candidate)

#### `RB-DRAIN-01`: Alarm-Driven Queue Drain Resuscitation
- **Objective**: Verify that the 1-minute alarm wakes an idle/terminated service worker and executes a queue drain pass.
- **Setup**: Seed `PENDING` queue item; allow service worker to become idle.
- **Action**: Trigger or wait for `chrome.alarms.onAlarm`.
- **Expected Result**: Service worker starts; `QueueDrainer.drain("alarm")` executes; item transitions to `COMPLETED`.
- **Invariants**: C-12 (Queue draining is bounded).

#### `RB-LOCKS-01`: Real Web Locks Mutual Exclusion
- **Objective**: Verify that `navigator.locks.request` prevents concurrent drain passes across simultaneous browser contexts.
- **Setup**: Two simultaneous drain requests initiated in extension context.
- **Action**: First worker holds lock; second worker requests exclusive lock with `{ ifAvailable: true }`.
- **Expected Result**: Second worker immediately yields (`null`) without executing concurrent operations.
- **Invariants**: I-14, I-15 (Mutual exclusion precedes mutation).

#### `RB-NET-01`: Service Worker Network Fetch via Host Permissions
- **Objective**: Verify that service worker can execute HTTPS requests to `api.github.com` (directed to a local mock HTTP server) without CORS blocks.
- **Setup**: Local mock GitHub server running on localhost; host permission configured.
- **Action**: `GitHubApiClient` executes GET and PUT requests from service worker.
- **Expected Result**: HTTP 200/201 responses received; headers include `Authorization` and `no-store`; zero CORS errors.
- **Invariants**: I-17, C-17.

#### `RB-ORIGIN-01`: Platform URL Injection Filtering
- **Objective**: Verify content script injects only on exact platform match patterns and ignores lookalike/unauthorized origins.
- **Setup**: Navigate browser to `https://leetcode.com` (supported) vs. `https://evil-leetcode.com` (unsupported).
- **Action**: Inspect DOM for content script execution.
- **Expected Result**: Content script active on `leetcode.com`; zero injection on `evil-leetcode.com`.
- **Invariants**: I-04 (Origin validation enforced).

## 12. Automation Strategy

For Phase 1D.1 execution:

1. **Framework**: **Playwright** (`@playwright/test`)
   - Native support for Chromium persistent contexts with `--load-extension`.
   - Native CDP (Chrome DevTools Protocol) session access for inspecting Service Workers (`ServiceWorker.stopWorker`, background console logs).
   - Support for Firefox extension testing via persistent context / Marionette.
2. **Profile Strategy**:
   - **Fresh Profile per Test Suite**: Every test runs in an isolated, temporary directory (`fs.mkdtempSync`) to prevent state bleed.
   - **Simulated Browser Restart**: Closing the Playwright context and relaunching with the **same** user data directory to test real cold-start durability (`RB-PERSIST-01`).
3. **Network Mocking Strategy**:
   - **Zero Live GitHub Traffic**: Tests must never send requests to public GitHub.
   - **Local Mock HTTP Server**: A lightweight, in-process Node.js `http.Server` running on `127.0.0.1` implementing the required GitHub REST API endpoints (`GET /repos/.../contents`, `PUT /repos/.../contents`, `GET /user`).
   - Requests directed via extension configuration or proxy routing.
