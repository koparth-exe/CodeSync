### C. Duplicate Identity Model

The active duplicate detection hierarchy in [`QueueManager.enqueueSubmission`](file:///d:/Parth/Projects/CodeSync/src/shared/queue/manager.ts#L80-L125) operates as follows for all items in `PENDING` or `PROCESSING` state:

```
[Incoming Submission]
         ↓
Hierarchy 1: raw.id && i.id === raw.id
         ├── MATCH → Return existing queue item
         └── NO MATCH
                  ↓
Hierarchy 2: raw.submissionId && i.submissionId
         ├── raw.platform === i.platform && raw.submissionId === i.submissionId
         │        ├── MATCH → Return existing queue item (same submission event delivered again)
         │        └── NO MATCH → DISTINCT SUBMISSIONS (Proceed to WAL enqueue; do NOT collapse)
         └── EITHER submissionId IS ABSENT
                  ↓
Hierarchy 3: !raw.submissionId && !i.submissionId
         ├── i.platform === raw.platform && i.problemSlug === raw.problemSlug && i.contentHash === contentHash
         │        ├── MATCH → Return existing queue item (duplicate delivery of unkeyed event)
         │        └── NO MATCH → Proceed to WAL enqueue
```

**Key Invariant**: Two submissions with different platform submission IDs (e.g. LeetCode submission #101 vs #102) will **never** be collapsed, even if `problemSlug` and `contentHash` are identical.

### D. Provenance Model

Extraction provenance and validation authority are strictly separated across all models, storage records, and WAL entries:

1. **Extraction Provenance (`sourceProvenance`)**:
   - Strictly documents *where and how* source code was extracted by the platform adapter.
   - Values: `AUTHORITATIVE_SUBMISSION_SOURCE`, `SUBMISSION_PAGE_SOURCE`, `EDITOR_SOURCE`, `DOM_FALLBACK_SOURCE`.
   - `AUTHORITATIVE_SUBMISSION_SOURCE` is strictly reserved for approved extension-controlled extraction contexts.
   - Editor code remains `EDITOR_SOURCE` throughout the entire lifecycle.
2. **Validation Authority (`validatedBy`)**:
   - Strictly documents *which trusted component performed authoritative schema validation and admitted the item into the durable queue*.
   - Value: `"SERVICE_WORKER"`.
   - Never alters or overwrites the underlying `sourceProvenance`.
3. **Immutability across Crashes**:
   - Both `sourceProvenance` and `validatedBy` are serialized into the WAL intent snapshot and restored during crash recovery.

### E. Target Authorization Model

Phase 1C.4.1 enforces a clear boundary between local configuration syntax validation and authoritative GitHub authorization:

1. **Local Syntactic & Structural Validation (Phase 1C.4.1)**:
   - Target repository syntax is verified via [`validateRepositoryIdentity`](file:///d:/Parth/Projects/CodeSync/src/shared/config/index.ts#L22-L22) (`owner/repo` pattern).
   - Target branch is verified via Safe Branch Grammar.
   - Base folder is verified via the 5-Pillar Path Engine.
   - Content scripts and webpage DOM cannot inject or override repository, branch, base path, or duplicate policy.
2. **Distinguishing Configured vs. Authorized**:
   - `authorizationStatus` in [`TargetSnapshot`](file:///d:/Parth/Projects/CodeSync/src/shared/storage/types.ts#L24-L35) records:
     - `"AUTHORIZED"`: If the repository already exists within `codesync:auth` (`authorizedRepositories`).
     - `"CONFIGURED_UNVERIFIED"`: If configured by the user locally without prior GitHub App verification.
3. **No Network Calls in 1C.4.1**:
   - No GitHub REST API calls are dispatched during enqueue.
   - Syntactic validity is never conflated with GitHub repository write authorization.
   - Phase 1C.4.2 / 1C.2.1 queue draining retains exclusive responsibility for verifying write permissions, repository existence, and repository numeric ID via `getRepository()` prior to any remote GitHub mutation.
