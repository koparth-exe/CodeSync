## 4. Current Lease Architecture

The lease architecture operates as a two-tier hybrid model:

```mermaid
flowchart TD
    Trigger[Drain Trigger: startup / alarm / submission] --> RunExclusively[QueueConcurrencyManager.runExclusively]
    RunExclusively --> WebLockCheck{Web Locks Supported & Available?}
    WebLockCheck -- Yes --> RequestWebLock[navigator.locks.request exclusive]
    WebLockCheck -- No / Throws --> Tier2Direct[Direct Tier 2 Fallback]
    RequestWebLock -- Lock Granted --> AcquireLease[Tier 2: acquirePersistentLease]
    RequestWebLock -- Lock Contended --> YieldNull[Yield null gracefully]
    Tier2Direct --> AcquireLease
    AcquireLease --> Probe[Step 1: Check existing lease in storage.local]
    Probe -- Active & Not Self --> YieldContended[Yield null: Active lease held]
    Probe -- Expired or None --> PreCommit[Step 2: Pre-commit recheck]
    PreCommit -- Interleaving Winner --> YieldInterleave[Yield null: Interleaving takeover]
    PreCommit -- Clear --> WriteCandidate[Write candidate lease: fencingToken N+1]
    WriteCandidate --> VerifyReadBack[Step 3: Verification read-back]
    VerifyReadBack -- Overwritten by Race --> YieldCollision[Yield null: Collision detected]
    VerifyReadBack -- Verified Self --> LeaseHeld[Lease Acquired Authoritatively]
    LeaseHeld --> Heartbeat[Start Heartbeat: every 10s renewHeartbeat]
    LeaseHeld --> DrainPass[Execute QueueManager.drainQueue]
    DrainPass --> ReleaseLease[finally: releaseLease matching workerId + fencingToken]
```

### Key Architectural Invariants
1. **Coordination vs Ownership:** Web Locks coordinate execution between currently running threads/tabs in the browser. The persistent lease in `browser.storage.local` authoritatively records ownership across process crashes and restarts.
2. **Probe-and-Verify:** In the absence of atomic Compare-And-Swap (CAS) in `browser.storage.local`, `acquirePersistentLease` executes a three-phase write protocol:
   - Read existing lease and compute `nextFencingToken`.
   - Pre-commit check immediately before write to detect interleaving competitors.
   - Post-commit verification read-back to verify that the caller's write was not overwritten by a concurrent race.

## 5. Current Fencing Architecture

Fencing tokens enforce monotonic generation sequencing:
1. **Generation:** When acquiring an expired lease or unowned queue, the new worker observes the existing lease's token `N` and persists `N + 1`.
2. **Authority Binding:** The worker execution closure binds `fencingToken` alongside its unique `workerId` (`crypto.randomUUID()`).
3. **Validation Call:** [validateFencingToken(workerId, fencingToken)](file:///d:/Parth/Projects/CodeSync/src/shared/queue/concurrency.ts#L152) reads `storage.getLease()`.
4. **Rejection Rule:** The call rejects fail-closed with [StaleLeaseError](file:///d:/Parth/Projects/CodeSync/src/shared/errors/index.ts) if:
   - `!existing` (lease was removed or expired),
   - `existing.workerId !== workerId` (superseded by another worker),
   - `existing.fencingToken !== fencingToken` (token generation mismatch), OR
   - `Date.now() > existing.expiresAt` (lease expired in wall-clock time).

## 6. Lease Durability Findings

1. **Storage Subsystem:**
   - The lease record is stored in `browser.storage.local` under the dedicated key `STORAGE_KEYS.QUEUE_LEASE = "codesync:queue_lease"` ([src/shared/storage/keys.ts](file:///d:/Parth/Projects/CodeSync/src/shared/storage/keys.ts)).
   - Persisted fields: `workerId`, `fencingToken`, `acquiredAt`, `expiresAt`, `maxLifetimeExpiresAt`, `triggerSource` ([src/shared/storage/types.ts:L100-L108](file:///d:/Parth/Projects/CodeSync/src/shared/storage/types.ts#L100-L108)).
2. **Worker Reconstruction:**
   - A newly booted Service Worker does not rely on any retained memory. On startup, [QueueManager.drainQueue](file:///d:/Parth/Projects/CodeSync/src/shared/queue/manager.ts#L392) re-reads the lease from `storage.local`.
   - In [tests/security/crash-boundary-recovery.test.ts:L86-L100](file:///d:/Parth/Projects/CodeSync/tests/security/crash-boundary-recovery.test.ts#L86-L100), Worker B starts with completely separate class instances and reconstructs lease authority solely from durable storage.
3. **Expiration Calculation:**
   - Calculated via `expiresAt = now + LEASE_TTL_MS` (30 seconds).
   - Enforces an absolute upper bound `maxLifetimeExpiresAt = now + MAX_WORKER_OWNERSHIP_MS` (5 minutes). Even if heartbeats continuously renew, `renewHeartbeat()` rejects renewals past 5 minutes ([src/shared/queue/concurrency.ts:L136](file:///d:/Parth/Projects/CodeSync/src/shared/queue/concurrency.ts#L136)).
4. **Clock Assumptions:**
   - Expiration compares `Date.now()` against durable timestamps.
   - Monotonicity does not depend on system time: the fencing counter increments as an integer (`existing.fencingToken + 1`). If the wall clock jumps backward, an active lease could appear non-expired longer (up to TTL), but fencing tokens cannot roll backward.

## 7. Fencing Findings

1. **Monotonicity Across Crashes:**
   - If Worker A holds lease token `1` and crashes, the lease remains in `storage.local` with `fencingToken: 1`.
   - When Worker B detects expiration, line 65 executes: `nextFencingToken = existing ? existing.fencingToken + 1 : 1`, producing `2`.
   - This increment is strictly monotonic across crash-recovery cycles.
2. **Orderly Release Counter Reset (Architectural Nuance):**
   - When a worker finishes queue processing normally, [releaseLease](file:///d:/Parth/Projects/CodeSync/src/shared/queue/concurrency.ts#L181) executes:
     ```ts
     if (existing && existing.workerId === workerId && existing.fencingToken === fencingToken) {
       await this.storage.removeLease();
     }
     ```
   - If no subsequent worker is active, the lease key is removed.
   - On the next distinct trigger (e.g. 10 minutes later), `existing` is `null`, and line 65 sets `nextFencingToken = 1`.
   - **Is this a stale-worker defect?** No. Stale-worker protection does **not** rely on token number alone; it relies on the tuple `(workerId, fencingToken, expiresAt)`. Since `workerId` is a cryptographically random UUID v4 generated per `runExclusively` execution, an old worker with token 1 from a previous session cannot pass `validateFencingToken` because `existing.workerId !== workerId`. If no lease exists, `!existing` rejects.
3. **Authoritative State Checking:**
   - Fencing is never checked against in-memory cached booleans. Every call to `validateFencingToken` invokes `await this.storage.getLease()`, directly hitting the storage driver.

## 8. Mutation-Boundary / TOCTOU Findings

The critical race analyzed is:
```
Worker A: validates lease/fence N
Worker A: starts asynchronous network work (GitHubContentsService)
Worker B: detects lease expiry, acquires lease N+1
Worker A: network work finishes, attempts durable mutation
```

### Trace Analysis in Production Code
In [src/shared/queue/manager.ts:L460-L465](file:///d:/Parth/Projects/CodeSync/src/shared/queue/manager.ts#L460-L465):
```ts
const result = await handler(item, payload);

// Fencing Check before committing handler outcome
await this.concurrency.validateFencingToken(workerId, fencingToken);
```
1. **Network Completion != Local Mutation Authority:** Even though Worker A's network call succeeded on GitHub, Worker A does **not** possess mutation authority upon return.
2. **Rejection at Boundary:** Line 463 executes `validateFencingToken(workerA, N)`. Storage contains Worker B's lease with `workerId: "Worker-B"` and `fencingToken: N+1`.
3. **Fail-Closed Abort:** `validateFencingToken` throws [StaleLeaseError](file:///d:/Parth/Projects/CodeSync/src/shared/errors/index.ts).
4. **Catch-Block Re-validation:** The error drops into the `catch (err)` block at line 547:
   ```ts
   // Fencing Check before writing error state
   await this.concurrency.validateFencingToken(workerId, fencingToken);
   ```
   Worker A calls `validateFencingToken` **again** before it can write a `FAILED` or `REQUIRES_ATTENTION` error state. It throws `StaleLeaseError` a second time, immediately aborting without executing `storage.setQueueMetadata`.
5. **No Release Hijacking:** In the `finally` block of `runExclusively`, Worker A calls `releaseLease(workerA, N)`. Line 185 checks `existing.workerId === workerA`. Because `existing.workerId` is Worker B, Worker A's release is a no-op and does not clear Worker B's lease.

## 10. Web Lock / Persistent Lease Findings

1. **Coordination vs Ownership:**
   - Web Locks (`navigator.locks`) are used strictly for in-session mutual exclusion to avoid unnecessary storage write contention.
   - If Web Locks succeed, `acquirePersistentLease` is still invoked inside the lock callback ([concurrency.ts:L251](file:///d:/Parth/Projects/CodeSync/src/shared/queue/concurrency.ts#L251)). Web Lock success never bypasses persistent leasing or fencing.
2. **Fallback Semantics:**
   - If `navigator.locks` throws an unexpected runtime error ([concurrency.ts:L258](file:///d:/Parth/Projects/CodeSync/src/shared/queue/concurrency.ts#L258)), the error is caught and execution falls back directly to Tier 2 persistent lease.
   - If `navigator.locks` is undefined (e.g. Firefox MV3 without Web Locks or non-supported context), line 264 executes `executeWithLease()` directly.
3. **Current Coverage Classification:**
   - Web Lock fallback resilience: **UNIT** (`concurrency-fencing.test.ts:L180-L270`)
   - Persistent lease without Web Lock: **INTEGRATION** (`CRASH-INT-05` explicitly disabled `navigator.locks` to test pure persistent fencing).

## 11. Concurrent Takeover Findings

Scenario: Worker A holds lease token `1`. Worker B and Worker C simultaneously attempt takeover upon expiration.

1. **Under Tier 1 (Web Locks Available):**
   - Web Locks API grants the exclusive lock to either Worker B or Worker C.
   - The winner acquires lease token `2`. The other yields immediately with `null`.
2. **Under Tier 2 Alone (Web Locks Absent or Thrown):**
   - Both workers execute `acquirePersistentLease`.
   - **Pre-commit Check ([L73](file:///d:/Parth/Projects/CodeSync/src/shared/queue/concurrency.ts#L73)):** If Worker B writes first, Worker C's pre-commit check observes Worker B's active lease and yields without writing.
   - **Verification Read-Back ([L99](file:///d:/Parth/Projects/CodeSync/src/shared/queue/concurrency.ts#L99)):** If Worker B and Worker C write candidate leases concurrently, the last write in storage wins. The loser reads back storage, detects `verified.workerId !== myWorkerId`, and yields with `reason: "Lease collision detected during verification read-back."`
3. **Risk Analysis:**
   - Two workers cannot both believe they hold an active lease. The verification read-back guarantees single ownership.

## 23. Verified Requirements

The following requirements are conclusively verified with direct evidence:
1. **Tier 1 / Tier 2 Separation:** Web Locks provide ephemeral mutual exclusion; persistent leases provide durable ownership across processes.
2. **Mutation-Boundary Revalidation:** Stale workers cannot commit successful synchronization results to `storage.local` after lease supersession (`CRASH-INT-05`).
3. **History Protection:** Stale workers cannot write duplicate history records to IndexedDB after lease supersession (`CRASH-INT-05`).
4. **Orderly Release Ownership Guard:** A stale worker cannot delete a newer worker's lease (`concurrency-fencing.test.ts`).
5. **Renewal Ownership Guard:** A stale worker cannot renew an expired or superseded lease (`concurrency-fencing.test.ts`).
6. **5-Minute Upper Bound:** Worker ownership is forcibly terminated at 5 minutes regardless of heartbeat renewal (`concurrency-fencing.test.ts`).
7. **Web Lock Fallback:** Safe fallback to persistent lease when Web Locks API throws or is missing (`concurrency-fencing.test.ts`).

## 24. Protected-but-Under-Tested Requirements

The following requirements are enforced by design in production code but lack dedicated integration/lifecycle test coverage:
1. **Multi-generation Monotonicity Across Repeated Takeovers:** Verified for 2 workers (`CRASH-INT-05`), but not tested across 3+ successive worker crashes/restarts (e.g. Worker A -> Worker B -> Worker C).
2. **Orderly Release Token Reset Dynamics:** When a worker finishes and deletes the lease via `releaseLease`, the next session starts from `fencingToken = 1`. The repository lacks an integration test verifying that a resurrected worker from the first session is rejected despite the token number recycling to 1.
3. **Handler-Error Path Mutation Boundary:** Revalidation at line 549 inside the catch block is verified by code inspection, but no integration test pauses a worker that subsequently *fails* its handler pass while superseded.
4. **Pure Tier 2 Acquisition Collision:** Probe-and-Verify collision handling when Web Locks are absent is tested at unit level, but not in a multi-worker concurrent integration test.
