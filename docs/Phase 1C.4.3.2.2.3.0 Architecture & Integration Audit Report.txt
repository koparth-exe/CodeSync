## 3. Retry State Model

The durable queue state machine is defined by [`QueueState`](file:///d:/Parth/Projects/CodeSync/src/shared/storage/types.ts#L11-L18) in `src/shared/storage/types.ts`:

- **`PENDING`**: Initial durable state upon validated enqueue. Immediately eligible for processing during drain.
- **`PROCESSING`**: Claimed exclusively by an authoritative worker under a validated lease fencing token. If interrupted by worker crash/suspension, `reconcileInterruptedItems()` increments `crashCount` (NOT `attempts`) and resets to `PENDING` (or quarantines to `REQUIRES_ATTENTION` if `crashCount >= 3`).
- **`COMPLETED`**: Terminal success state (`commitSha` and `commitUrl` populated). Never eligible for retry. Archived to `SyncHistoryEntry` in IndexedDB.
- **`SKIPPED`**: Terminal skip state (content identical to remote per duplicate policy). Never eligible for retry.
- **`FAILED`**: Non-terminal retryable failure state. Has `attempts >= 1`, `nextRetryAt` populated, and `lastError` recorded.
  - **Eligibility condition**: `item.state === QueueState.FAILED && (item.nextRetryAt ?? 0) <= now`.
  - If `now < nextRetryAt`: Skipped cleanly during queue drain.
  - If `now >= nextRetryAt`: Eligible for re-claim into `PROCESSING`.
- **`REQUIRES_ATTENTION`**: Terminal quarantine state. Applied when:
  - `attempts >= MAX_ATTEMPTS (5)` (exhausted retries).
  - `crashCount >= POISON_PILL_CRASH_THRESHOLD (3)` (poison-pill isolation).
  - Unrecoverable validation errors, auth failures (401/403 forbidden), path security violations, or missing payloads.
  - Never eligible for automatic retry; requires manual user review or configuration update.

### State Transition & Timing Lifecycle
1. **Creation**: Enqueued via `QueueManager.enqueueSubmission()` in `PENDING` state with `attempts: 0`, `crashCount: 0`, and `nextRetryAt: undefined`.
2. **Claim**: `drainQueue()` validates fencing token, transitions item to `PROCESSING`, records `fencingToken`, and persists metadata before invoking handler.
3. **Execution Failure**: Handler returns `status: "failed"`.
4. **Attempt Increment**: `item.attempts += 1` occurs inside `drainQueue()`.
5. **Backoff / Rate Limit Calculation**: `effectiveDelay = Math.max(computeBackoffDelay(item.attempts), rateLimitDelay)` is computed.
6. **Retry Scheduling**: `item.nextRetryAt = Date.now() + effectiveDelay`, `item.state = QueueState.FAILED`.
7. **Fenced Persistence**: Fencing token re-validated and written to `browser.storage.local`.
8. **Clearance**: On eventual successful retry, item transitions to `COMPLETED` and is purged after retention expiration via `purgeCompleted()`.

## 5. Backoff Analysis

- **Location**: [`src/shared/queue/backoff.ts`](file:///d:/Parth/Projects/CodeSync/src/shared/queue/backoff.ts#L1-L22).
- **Constants**:
  - `BASE_DELAY_MS = 2000` (2 seconds).
  - `MAX_DELAY_MS = 120_000` (2 minutes / 120 seconds).
  - `BACKOFF_FACTOR = 2`.
  - `JITTER_FRACTION = 0.2` (±20% uniform randomization).
- **Formula**:
  $$\text{safeAttempt} = \max(1, \lfloor \text{attempt} \rfloor)$$
  $$\text{rawDelay} = \min(\text{BASE\_DELAY\_MS} \times \text{BACKOFF\_FACTOR}^{\text{safeAttempt} - 1}, \text{MAX\_DELAY\_MS})$$
  $$\text{jitter} = \text{rawDelay} \times (\text{random}() \times 2 \times \text{JITTER\_FRACTION} - \text{JITTER\_FRACTION})$$
  $$\text{delay} = \max(0, \text{round}(\text{rawDelay} + \text{jitter}))$$
- **Attempt Input**:
  In `QueueManager.drainQueue()`, `item.attempts += 1` occurs **before** `computeBackoffDelay(item.attempts)`.
  - Attempt 1: $2000 \times 2^0 = 2000\,\text{ms} \pm 400\,\text{ms}$ (1.6s – 2.4s).
  - Attempt 2: $2000 \times 2^1 = 4000\,\text{ms} \pm 800\,\text{ms}$ (3.2s – 4.8s).
  - Attempt 3: $2000 \times 2^2 = 8000\,\text{ms} \pm 1600\,\text{ms}$ (6.4s – 9.6s).
  - Attempt 4: $2000 \times 2^3 = 16000\,\text{ms} \pm 3200\,\text{ms}$ (12.8s – 19.2s).
  - Attempt 5: Reaches `MAX_ATTEMPTS = 5` $\rightarrow$ quarantined to `REQUIRES_ATTENTION`.
- **Clamping**: Clamped at upper bound by `MAX_DELAY_MS` (120,000 ms) and lower bound by `Math.max(0, ...)`.
- **Restart Behavior**:
  Backoff is computed **at failure time** and committed into durable `item.nextRetryAt`.
  Worker restart does **not** reset backoff, does **not** recalculate backoff, and does **not** increment attempts. Fresh workers directly read the existing `nextRetryAt` from `browser.storage.local`.

## 7. Secondary Rate-Limit Analysis

- **HTTP Conditions**:
  - `res.status === 403` and `headers.get("retry-after")` is present (lines 284–299 in `client.ts`).
  - `rateLimit.remaining > 0` (or not 0).
- **Distinction from Authorization Failure**:
  - If `res.status === 403` with `Retry-After`: Classified as abuse detection / secondary throttling. Throws `GitHubRateLimitError` with `isSecondary: true`.
  - If `res.status === 403` without `Retry-After` and without `remaining === 0`: Classified as authentic authorization failure. Throws `GitHubApiError` with `code: ErrorCode.GITHUB_FORBIDDEN`, which `github-handler.ts` maps to `status: "requires_attention"` (`retryable: false`).
  - Secondary throttling is thus strictly prevented from degrading into permanent authorization rejection.
- **Parsing & Fallbacks**:
  - `const retryAfterSec = parseInt(retryAfterHeader, 10);`
  - Fallback: `const validRetryAfter = !isNaN(retryAfterSec) ? retryAfterSec : 60;` (fail-safe 60 seconds).
  - `resetTimestamp: Date.now() + validRetryAfter * 1000`.
- **Propagation**:
  Mapped in `QueueManager` to `rateLimitDelay = result.error.retryAfterSeconds * 1000`, dominating shorter backoffs and persisting to `item.nextRetryAt`.

## 9. Uncertain-Write Analysis

- **Strict Separation**:
  - **Transport-level PUT Failure** (`err.isRetryable || err.message.includes("timed out") || err.message.includes("Network failure")`):
    The client cannot know if GitHub received and committed the blob. It invokes `this.reconcileUncertainWrite()`. If the remote content hash matches, it marks the write confirmed. If it does not match, it throws `GitHubWriteOutcomeUnknownError`.
    In `github-handler.ts` (lines 540–550), `GitHubWriteOutcomeUnknownError` maps to `status: "requires_attention"` (`retryable: false`). Blind retry is forbidden.
  - **Known HTTP 429 / 403 Rate Limit**:
    The server responded definitively with a rejection code. The write outcome is 100% certain: it did **not** commit. It bypasses reconciliation and schedules an ordinary retry with delay.

## 10. Restart Analysis

- **Worker Lifecycle Tracing**:
  1. Worker A encounters retryable failure (rate limit or backoff).
  2. Worker A calculates `nextRetryAt = Date.now() + effectiveDelay`.
  3. Worker A validates its fencing token and persists `QueueItemMetadata` to `browser.storage.local`.
  4. Worker A terminates (OS suspension, idle termination, crash).
  5. Worker B initializes in a completely fresh execution context.
  6. Worker B reads `codesync:queue:metadata` via `storage.getQueueMetadata()`.
  7. Worker B executes WAL & orphan reconciliation (`reconcileWalAndOrphans`) and crashed item reconciliation (`reconcileInterruptedItems`).
     - *Crucial*: `reconcileInterruptedItems` only scans for items in `QueueState.PROCESSING`.
     - Items in `QueueState.FAILED` with `nextRetryAt` in the future are left completely untouched in `FAILED` state.
  8. Worker B drains queue: `isEligible = PENDING || (FAILED && nextRetryAt <= now)`.
  9. For an item where `now < nextRetryAt`, `isEligible` evaluates to `false`. Worker B skips the item without network calls or state mutation.
- **Evidence**:
  Proven in `CRASH-INT-04` (`tests/security/crash-boundary-recovery.test.ts:326-402`), where Worker B restarts, confirms durable `FAILED` state, `attempts: 1`, `nextRetryAt`, and skips early drain with zero PUT calls.

## 12. Lease / Fencing Analysis

- **Two-Tier Concurrency Architecture**:
  - **Tier 1**: Native Web Locks (`codesync_queue_drain`) for in-session mutual exclusion.
  - **Tier 2**: Persistent Lease (`codesync:queue:lease`) in `browser.storage.local` with monotonic fencing tokens (`fencingToken`).
- **Mutation Boundaries**:
  Every durable mutation path in `QueueManager` enforces fencing validation:
  1. WAL/Orphan metadata recovery: `validateFencingToken(workerId, fencingToken)` (line 345).
  2. WAL entry deletion: `validateFencingToken(workerId, fencingToken)` (line 352).
  3. Interrupted item crash reconciliation: `validateFencingToken(workerId, fencingToken)` (line 402).
  4. Item transition to `PROCESSING`: `validateFencingToken(workerId, fencingToken)` (line 461).
  5. Missing payload quarantine: `validateFencingToken(workerId, fencingToken)` (line 473).
  6. Handler outcome commit (`completed`, `skipped`, `failed`, `requires_attention`): `validateFencingToken(workerId, fencingToken)` (line 491).
  7. Catch-block exception handling: `validateFencingToken(workerId, fencingToken)` (line 577).
- **Lease Expiration / Supersession Scenario**:
  If Worker A (fence $N$) stalls during write and Worker B acquires the lease (fence $N+1$):
  When Worker A resumes and calls `validateFencingToken(workerId, fencingToken)`, it reads `codesync:queue:lease` from `browser.storage.local`.
  Because `existing.fencingToken ($N+1$) !== fencingToken ($N$)`, it throws `StaleLeaseError`.
  Worker A's mutation is aborted before `storage.setQueueMetadata()` can execute.
- **Evidence**:
  Formally verified in `FENCE-INT-03` (`tests/security/persistent-lease-fencing.test.ts:300-396`), where stale Worker A is rejected with `StaleLeaseError` and prevented from overwriting Worker B's completed state, incrementing attempts, or scheduling a retry.

## 13. Retry Storm Analysis

The architecture prevents retry storms via four coordinated defense layers:
1. **Durable Eligibility Timestamp**: `nextRetryAt` is committed to `browser.storage.local`. Worker restart does not wipe this timestamp.
2. **Mutual Exclusion**: Only one worker can hold the persistent lease (`codesync:queue:lease`) and Web Lock (`codesync_queue_drain`). Concurrent alarm or startup triggers gracefully return `null` immediately when contended.
3. **Exponential Backoff with Jitter**: `computeBackoffDelay()` applies exponential doubling ($2s, 4s, 8s, 16s$) with $\pm 20\%$ uniform jitter, preventing synchronized request bursts across items.
4. **Terminal Retry Ceiling**: Hard cutoff at `MAX_ATTEMPTS = 5` moves chronically failing items to `REQUIRES_ATTENTION`, terminating the retry loop.

## 14. Clock / Timestamp Analysis

- **Consistency of Units**:
  - `Date.now()` produces epoch milliseconds.
  - `x-ratelimit-reset` is in epoch seconds; multiplied by $1000$ to epoch milliseconds in `client.ts` (`parseInt(resetStr, 10) * 1000`).
  - `retry-after` is in seconds; multiplied by $1000$ to milliseconds in `manager.ts` (`retryAfterSeconds * 1000`).
  - `backoffDelay` is in milliseconds.
  - `item.nextRetryAt` is stored strictly in epoch milliseconds.
  - Comparison in `drainQueue` compares `(item.nextRetryAt ?? 0) <= Date.now()` (ms to ms).
- **Negative Delay & Overflow Protection**:
  - `Math.max(0, result.error.resetTimestamp - Date.now())` guards against past/stale reset timestamps.
  - `Math.max(0, ...)` guards jitter calculations against negative delay values.
  - `isNaN()` checks in `client.ts` fall back to conservative defaults (e.g. 60s).

## 15. Fail-Closed Analysis

- **Missing `nextRetryAt`**:
  If an item is in `QueueState.FAILED` with `nextRetryAt: undefined`, `(item.nextRetryAt ?? 0) <= now` evaluates to `0 <= now` (true). The item is treated as eligible for its next attempt, but its accumulated `attempts` count is preserved. Upon another failure, `attempts` increments toward the terminal limit of 5.
- **Corrupted Durable Metadata**:
  `StorageService.getQueueMetadata()` validates each item in `codesync:queue:metadata`. If the array contains non-object or invalid elements, corrupted items are isolated to `codesync:corrupted` (`isolateCorrupted`), and only valid items are processed.
- **Missing Payload**:
  If an eligible metadata record references a missing IndexedDB payload, it transitions to `REQUIRES_ATTENTION` with `ErrorCode.PAYLOAD_NOT_FOUND` under fencing validation, preventing infinite processing loops.

## 19. Test Evidence Gaps

The following specific test evidence gaps have been identified for closure in targeted test implementation phases:

1. **Multi-Worker Attempt Chain (`RETRY-REC-04`)**:
   Evidence is lacking that an item failing across successive independent workers ($Worker_A \rightarrow Worker_B \rightarrow Worker_C$) increments `attempts` monotonically ($1 \rightarrow 2 \rightarrow 3$) without resetting to 0, and cleanly transitions to `REQUIRES_ATTENTION` when `attempts >= 5`.
2. **Successive Restart Idempotency Without Clock Advancement (`RETRY-REC-03` / `RATE-REC-08`)**:
   Evidence is lacking that cycling through 3+ worker restarts ($A \rightarrow B \rightarrow C$) while `now < nextRetryAt` produces zero timestamp drift, zero state mutations, zero attempt increments, and zero crashCount increments.
3. **Primary Rate Limit (403 Remaining = 0) Across Restart (`RATE-REC-01`)**:
   Evidence is lacking that an HTTP 403 response with `x-ratelimit-remaining: "0"` and `x-ratelimit-reset` header persists its reset timestamp into `nextRetryAt` and is strictly honored by a reconstructed fresh worker.
4. **Secondary Rate Limit (403 + Retry-After) Across Restart (`RATE-REC-02`)**:
   Evidence is lacking that an HTTP 403 response with `Retry-After` header (abuse detection throttle) persists its delay into `nextRetryAt` and is strictly honored by a reconstructed fresh worker.
5. **Effective Delay Dominance Across Worker Reconstruction (`RATE-REC-03`)**:
   Evidence is lacking that when both exponential backoff and rate-limit delay apply, the calculated dominant delay survives worker reconstruction and governs eligibility in Worker B.

## 20. Security / Reliability Assessment

- **Retry Persistence**: Retry state is completely decoupled from worker memory and persisted to `browser.storage.local`. Invariant verified.
- **Rate-Limit Persistence**: Primary and secondary rate-limit delays are translated into absolute epoch timestamps and durably committed. Invariant verified.
- **Fencing Protection**: Stale workers cannot overwrite retry state or schedule obsolete retries. Invariant verified.
- **Restart Resilience**: Fresh workers boot, reconcile WAL and crashed items without disturbing `FAILED` items, and respect `nextRetryAt`. Invariant verified.
- **Retry Storm Prevention**: Fencing, two-tier locks, exponential backoff with jitter, and max attempts protect against storms. Invariant verified.
- **Uncertain Writes**: Known 429 / 403 rate limits never trigger uncertain-write reconciliation; transport PUT errors never trigger blind retries. Invariant verified.
- **Idempotency**: Draining a queue where items are not eligible produces zero mutations and zero network requests. Invariant verified.

## 23. Remaining Limitations

1. **Automated Integration Evidence vs. Real Browser Lifecycle**:
   Vitest integration tests with mocked storage and fake IndexedDB provide high confidence in algorithm and protocol correctness, but do not reproduce actual OS-level process termination, memory eviction under mobile/desktop constraints, or browser profile migration.
2. **System Clock Slew**:
   Calculations assume monotonic forward progression of `Date.now()`. System clock backward step while a worker is stopped could cause a future `nextRetryAt` to be considered eligible prematurely.
