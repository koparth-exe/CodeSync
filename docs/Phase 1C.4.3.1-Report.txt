## 3. E2E Test Architecture

### 3.1 Component Wiring via Existing Seams
The pipeline harness connects real production services using their existing constructor seams:
1. **Durable Storage**: `MemoryStorageDriver` (implementing `StorageDriver` for `chrome.storage.local`) and `MemoryPayloadStorageDriver` (implementing `PayloadStorageDriver` for IndexedDB) provide isolated in-memory persistence without cross-test leakage.
2. **Background Dispatch**: `harness.dispatchBackgroundMessage` executes the exact message validation routine found in `src/entrypoints/background.ts`:
   - Validates `sender.id === chrome.runtime.id`
   - Validates `sender.url` matches trusted platform origins (`PLATFORM_ORIGINS`)
   - Enforces `isExtensionMessage` schema check
   - Enforces nonce unicity and UUID v4 format via `SubmissionHandler.handleMessageAndEnqueue`
3. **Queue Execution**: `QueueDrainer` drains queue items via `GitHubQueueSyncHandler`, which claims durable leases via `QueueConcurrencyManager` and drives `GitHubContentsService`.
4. **Network Isolation**: `GitHubContentsService` is injected with a custom `fetchFn` backed by `MockGitHubServer.handleFetch`. No network sockets are opened; `api.github.com` is never contacted.

### 3.2 Virtual Time & Lease Invariant Control
Time is controlled deterministically via Vitest's `vi.spyOn(Date, "now")` through `harness.advanceTime(ms)`:
- Leases, exponential backoff, retry windows, and alarm schedules advance instantaneously without `setTimeout` delays.
- Virtual time initializes from `Math.floor(Date.now() / 1000) * 1000`, guaranteeing positive monotonic time progression.

## 9. Findings & Observations

### P2 Observation: Rate-Limit Catch Scope in `GitHubContentsService`
- **Location**: [`src/shared/github/contents-service.ts`](file:///d:/Parth/Projects/CodeSync/src/shared/github/contents-service.ts#L364)
- **Detail**: In `createOrUpdateFile`:
  ```typescript
  if (err instanceof GitHubApiError && (err.isRetryable || ...)) {
    return this.reconcileUncertainWrite(...);
  }
  ```
  Because `GitHubRateLimitError` inherits from `GitHubApiError` with `isRetryable = true`, a 429 encountered during a `PUT` request will enter the uncertain-write reconciliation block rather than bubbling up directly to `GitHubQueueSyncHandler.handle`.
- **Impact in Phase 1C.4.3.1**: In Scenario E2E-07, pre-flight `GET` requests subjected to 429 correctly bubble to `GitHubQueueSyncHandler`, setting `nextRetryAt` and delaying subsequent drain passes. No production change was made in order to adhere strictly to the zero-production-modification constraint. It is recommended to refine this catch block in a future maintenance cycle so that 429 errors during PUT also bubble rate-limit delays directly.
