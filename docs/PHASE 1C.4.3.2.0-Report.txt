## 8. Interrupted PROCESSING Recovery Audit

- **Identification:** In [manager.ts:353-386](file:///d:/Parth/Projects/CodeSync/src/shared/queue/manager.ts#L353-L386) (`reconcileInterruptedItems`), any item where `item.state === QueueState.PROCESSING` is identified as interrupted. Because this method executes inside `concurrency.runExclusively`, no active worker is processing the item; it was abandoned by a terminated context.
- **Accounting:**
  - `item.crashCount += 1` is monotonically incremented.
  - `item.attempts` is **NOT** modified. `attempts` tracks external sync failures (e.g. network drops, HTTP errors), whereas `crashCount` tracks worker termination.
- **State Transition:**
  - If `item.crashCount < POISON_PILL_CRASH_THRESHOLD` (threshold = 3): `item.state = QueueState.PENDING`.
  - If `item.crashCount >= 3`: `item.state = QueueState.REQUIRES_ATTENTION` with `ErrorCode.POISON_PILL_DETECTED`.
- **Idempotency:**
  - If `reconcileInterruptedItems()` is executed twice consecutively, the first pass converts all `PROCESSING` items to `PENDING` (or `REQUIRES_ATTENTION`).
  - The second pass encounters zero `PROCESSING` items and makes zero modifications. Recovery is strictly idempotent.

## 9. Retry / Rate-Limit Persistence Audit

- **Durable Fields:** When a retryable failure occurs (e.g. network error, 5xx server error, or 429 rate limit), [manager.ts:509-536](file:///d:/Parth/Projects/CodeSync/src/shared/queue/manager.ts#L509-L536) commits:
  - `item.state = QueueState.FAILED`
  - `item.attempts += 1`
  - `item.nextRetryAt = Date.now() + effectiveDelay`
  - `item.lastError = { code, message, timestamp }`
- **Rate-Limit Dominance:** `effectiveDelay = Math.max(backoffDelay, rateLimitDelay)` guarantees that a server-dictated `Retry-After` (or `resetTimestamp`) dominates exponential backoff.
- **Restart Survival:**
  - All four fields reside in `browser.storage.local`.
  - When the service worker restarts, `reconcileInterruptedItems()` ignores `FAILED` items.
  - `drainQueue()` evaluates eligibility: `item.state === PENDING || (item.state === FAILED && item.nextRetryAt <= now)`.
  - If virtual time is before `nextRetryAt`, the item is safely skipped. Delay is not lost, attempts are not reset, and no premature PUT is issued.

## 10. Uncertain-Write + Restart Audit

- **Scenario:** PUT dispatched -> network drop / timeout -> service worker terminates before reconciliation.
- **Durable State at Crash:** Item is `PROCESSING` in `storage.local`. Remote write is unconfirmed.
- **Restart Execution:**
  1. Service worker starts up.
  2. `reconcileInterruptedItems()` restores item to `PENDING`, `crashCount = 1`.
  3. `drainQueue()` claims item -> transitions to `PROCESSING`.
  4. Invokes `GitHubContentsService.synchronizeFile()`.
  5. **STEP 6 PRE-FLIGHT GET:** Executes an authoritative GET for the target file before issuing any write.
     - *If prior write succeeded on GitHub:* Remote file exists and `remoteFile.contentHash === localContentHash`. Duplicate policy (`REPLACE_IF_DIFFERENT`) returns `status: "skipped_identical"`. **Zero duplicate PUT is issued.** Item transitions to `SKIPPED` and completes cleanly.
     - *If prior write did NOT reach GitHub:* Remote file is absent (or older version). SynchronizeFile performs safe PUT with remote `sha`.
- **Verdict:** **Zero blind PUT vulnerability.** The mandatory Step 6 pre-flight GET guarantees that restart after an uncertain write cannot issue a blind duplicate write.

## 11. Confirmed-Write + Restart Audit

- **Scenario:** PUT succeeds -> HTTP 200/201 response received -> service worker terminates before `QueueManager` commits `item.state = COMPLETED`.
- **Durable State at Crash:** GitHub has committed the file. `storage.local` still lists the item as `PROCESSING`.
- **Restart Execution:**
  1. `reconcileInterruptedItems()` restores item to `PENDING`, `crashCount = 1`.

  5. Under default policy `REPLACE_IF_DIFFERENT`, handler returns `skipped_identical`.
  6. QueueManager transitions item to `SKIPPED` and appends `SyncHistoryEntry` (status: `"skipped"`).
- **Verdict:** Safe. No duplicate commit is created on GitHub. The submission transitions out of the active queue to a terminal state without data loss.

- **Current Mitigation:** Built directly into production architecture.
- **Recommendation:** None; architecture adheres to approved recovery contract.

### FINDING-02 — INFO (KEEP_ALL POLICY RECOVERY CHARACTERISTIC)
- **Evidence:** [src/shared/github/contents-service.ts:547-595](file:///d:/Parth/Projects/CodeSync/src/shared/github/contents-service.ts#L547-L595)
- **File/Symbol:** `GitHubContentsService.resolveKeepAllPath`
- **Scenario:** Under `KEEP_ALL` policy, if a worker crashes after writing the base file but before local completion, recovery on restart will find the base file exists and resolve to `-v2`.
- **Impact:** By definition, `KEEP_ALL` creates versioned files for each sync. This is expected behavior for `KEEP_ALL` when an interrupted write cannot be distinguished from a subsequent user submission.
- **Current Mitigation:** Default duplicate policy is `REPLACE_IF_DIFFERENT`, which skips identical content cleanly via Step 7.
- **Recommendation:** Document this property in recovery specifications.
- **Blocks 1C.4.3.2.1:** NO.
