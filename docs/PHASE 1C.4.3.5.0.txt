  │    - In-memory anti-replay cache (seenNonces)
  │    - deriveTrustedSenderContext(runtimeSender):
  │        * runtimeSender.tab -> "content-script"
  │        * runtimeSender.url -> "popup" / "options"
  │        * runtimeSender.id -> "background"
  │    - CONTEXT_ALLOWED_ACTIONS allowlist (content-script limited to 3 types)
  │
  ▼ [ SubmissionHandler.handleMessageAndEnqueue ]

  │       - Freezes TargetSnapshot (Object.freeze)
  │  7. Sets validatedBy: "SERVICE_WORKER"
  │
  ▼ [ DURABLE MUTATION: QueueManager.enqueueSubmission ]
  │  1. Queue capacity check (<= 200 active items)
  │  2. Deduplication check (Hierarchy 1: ID, 2: platform+submissionId, 3: platform+slug+hash)
  │  3. Persist WAL INTENT to IndexedDB (wal_logs)
  │  4. Persist payload to IndexedDB (payloads)
  │  5. Persist lightweight QueueItemMetadata to storage.local

  ▼ [ CONCURRENCY & FENCING LEASE: QueueConcurrencyManager ]

## 5. Trust Boundary Analysis

### 5.1 Submission / Adapter Boundary
- **Untrusted Component**: The webpage DOM, third-party page scripts, ad networks, and DOM event dispatchers.
- **Semi-Trusted Component**: The content script running in an MV3 isolated world.
- **Architectural Defense**:
  - The content script does not trust window messages or arbitrary global variables.
  - Candidate extraction yields purely structural proposal data (`CanonicalSubmissionCandidate`), not execution authorization.
  - The adapter's `validateAuthoritativeSource` strictly rejects page-supplied strings, objects without `authority: "EXTENSION_INTERNAL"`, or payloads lacking the internal `EXTENSION_AUTHORITY_TOKEN`.
  - Content scripts cannot access extension storage or trigger background state mutations directly.

### 5.2 Message Boundary
- **Transport**: `browser.runtime.sendMessage` from content script / extension frames to `background.ts`.
- **Architectural Defense**:
  - The message envelope is validated via [MessageEnvelopeValidator](file:///d:/Parth/Projects/CodeSync/src/shared/messaging/validator.ts#L62-L235).
  - Sender context is authoritatively derived from browser runtime metadata (`runtimeSender.tab`, `runtimeSender.url`, `runtimeSender.id`), completely ignoring the caller's claimed body field.
  - Context allowlists (`CONTEXT_ALLOWED_ACTIONS`) strictly forbid `content-script` from dispatching privileged configuration, authentication, or retry actions.
  - Anti-replay enforces UUID v4 nonces and sliding window timestamps (-5s future skew, +30s max age).
  - `wxt.config.ts` declares zero `externally_connectable` permissions, preventing external web pages from sending runtime messages to CodeSync.

### 5.3 Validation Authority Boundary
- **Distinction**: Source provenance (`sourceProvenance`) vs. validation authority (`validatedBy`).
- **Architectural Defense**:
  - `validatedBy` is never accepted from incoming messages.
  - [SubmissionHandler](file:///d:/Parth/Projects/CodeSync/src/shared/adapters/submission-handler.ts) constructs a fresh `NormalizedSubmission` record where `validatedBy: "SERVICE_WORKER"` is stamped internally solely after all envelope, origin, schema, character hygiene, status, and normalization validations pass.
  - [GitHubQueueSyncHandler](file:///d:/Parth/Projects/CodeSync/src/shared/queue/github-handler.ts) enforces that `item.validatedBy === "SERVICE_WORKER"`. Any queue item lacking this stamp is immediately quarantined into `REQUIRES_ATTENTION` with zero network calls.

### 5.4 Submission Identity Boundary
- **Distinction**: Submission identity vs. content identity.
- **Architectural Defense**:
  - Primary identity: `platform + submissionId`.
  - Fallback identity (only when both submissions lack `submissionId`): `platform + problemSlug + contentHash`.
  - Submissions with distinct `submissionId` values are never collapsed, even if `platform`, `problemSlug`, and `contentHash` are identical (verified in `IDEM-INT-05`).
  - Equal `contentHash` does not collapse submissions across different targets or platforms.

### 5.5 Target Authorization Boundary
- **Distinction**: Local target configuration vs. remote GitHub authorization.
- **Architectural Defense**:
  - [TargetSnapshot](file:///d:/Parth/Projects/CodeSync/src/shared/storage/types.ts#L24-L37) is captured at enqueue time and deeply frozen (`Object.freeze`).
  - Runtime mutations to extension configuration in `storage.local` cannot mutate pending or processing queue items.
  - Local configuration cannot bypass GitHub authorization: `TargetSnapshot.authorizationStatus` tags unverified local repos as `CONFIGURED_UNVERIFIED`.
  - During drain, [GitHubContentsService](file:///d:/Parth/Projects/CodeSync/src/shared/github/contents-service.ts) performs live authoritative validation via `getRepository(owner, repo)`. If GitHub denies access (404/403), the item is quarantined fail-closed.

### 5.6 Queue / WAL Boundary
- **Structure**: Hybrid storage architecture (lightweight metadata in `browser.storage.local`, heavy payloads and WAL logs in IndexedDB).
- **Architectural Defense**:
  - Intent-first Write-Ahead Log: WAL entry in `INTENT` phase is persisted to IndexedDB *before* payload or metadata mutations begin.
  - Crash recovery is idempotent: incomplete intents are reconciled upon startup; uncommitted WAL entries without payloads are discarded; payloads without metadata are quarantined; metadata without payloads is quarantined.
  - Capacity bounds: queue length strictly capped at 200 active items (`MAX_QUEUE_ITEMS`).

### 5.7 GitHub Authorization Boundary
- **Authentication vs. Authorization**: Authentication establishes the user's identity; authorization establishes whether the user's token possesses push permissions for the specific target repository.
- **Architectural Defense**:
  - Every write pass executes live `getRepository(owner, repo)` and `getBranch(owner, repo, branch)`.
  - Denial of authorization (HTTP 403 or 404) immediately halts execution and transitions the item to `REQUIRES_ATTENTION` (`GITHUB_FORBIDDEN` or `GITHUB_REPOSITORY_NOT_FOUND`).
  - Authorization failures consume zero retries (`attempts` remains unchanged) and never fall back to another repository, branch, or credential.

### 5.8 GitHub Write Boundary
- **Protocol**: 12-Step Validated Transactional Write Protocol with Optimistic Concurrency Control (OCC).
- **Architectural Defense**:
  - Pre-flight remote state GET obtains current remote blob SHA.
  - PUT requests include the remote blob SHA for server-enforced optimistic concurrency.
  - Remote HTTP 409 Conflict triggers fresh authoritative GET, duplicate re-evaluation, and fresh SHA acquisition (strictly capped at `MAX_CONFLICT_REVALIDATIONS = 2`).
  - Post-write verification GET guarantees that remote file matches intended content hash.
  - Uncertain write outcomes (network timeout/drop during PUT dispatch) invoke `reconcileUncertainWrite` via fresh GET; if remote does not match, throws `GitHubWriteOutcomeUnknownError` and quarantines. Zero blind retry writes are ever dispatched.

### 5.9 Path Security Boundary
- **Engine**: Three-Pillar Path Security Engine ([path-engine.ts](file:///d:/Parth/Projects/CodeSync/src/shared/github/path-engine.ts)).
- **Architectural Defense**:
  - Bounded URL decoding (max 3 cycles); rejects lingering percent-encoding.
  - Strict POSIX portable ASCII character grammar (`^[a-zA-Z0-9_.-]+$`).
  - Absolute rejection of all non-ASCII characters, Unicode homoglyphs, bidirectional overrides, and zero-width codepoints.
  - Absolute rejection of NUL bytes, control bytes (`\x00-\x1F`, `\x7F-\x9F`), and whitespace.
  - Absolute rejection of forward-slash absolute paths (`/`), Windows drive prefixes (`C:`), and UNC paths (`//`, `\\\\`).
  - Traversal defense: rejects `.` and `..` segments, internal `..`, and leading/trailing dots.
  - Reserved name blocking: case-insensitive DOS device names (`CON`, `PRN`, `AUX`, `NUL`, `COM1-9`, `LPT1-9`) with or without extensions.
  - Internal Git directory protection: `.git` and `.github`.
  - Structural limits: segment length <= 100, path depth <= 10 levels, total path length <= 255 characters.
  - Base folder containment: guarantees target resides within configured `baseFolder`.

### 5.10 Queue Drain Boundary
- **Concurrency**: Two-tier concurrency coordination.
  - Tier 1: In-session mutual exclusion via Web Locks API (`navigator.locks`).
  - Tier 2: Cross-session durable coordination via persistent lease in `storage.local` with monotonic fencing tokens and Probe-and-Verify.
- **Architectural Defense**:
  - Monotonically increasing `fencingToken` issued on lease acquisition.
  - `validateFencingToken(workerId, fencingToken)` is validated prior to every state transition, payload quarantine, and outcome commit.
  - Stale workers whose lease expired or was superseded throw `StaleLeaseError` and are completely barred from mutating queue state, deleting WAL records, or recording history.

### 5.11 Persistence Boundary
- **Storage Durability vs. Trust**: Storage is durable but treated as unverified input upon deserialization.
- **Architectural Defense**:
  - Deserialized queue items undergo structural validation in [GitHubQueueSyncHandler](file:///d:/Parth/Projects/CodeSync/src/shared/queue/github-handler.ts).
  - Source payload retrieved from IndexedDB has its SHA-256 content hash recomputed and verified against `item.contentHash`. Any tampering results in immediate quarantine.
  - Corrupted storage records are quarantined to `codesync:quarantined_storage` without causing application crashes.

## 6. Adversarial Threat Model (Threats A–O)

### A. Hostile Webpage
- **Scenario**: A malicious coding platform webpage, compromised ad script, or injected DOM element attempts to forge accepted status, inject fake submission IDs, alter source code, or trigger unauthorized synchronizations.
- **Mitigation**: Content script runs in an MV3 isolated world. Candidate extraction yields unprivileged proposal data. The trusted service worker validates sender tab URL against adapter approved origins via `validatePlatformOrigin`, validates schema via `validateCanonicalSubmission`, enforces `status === "ACCEPTED"`, normalizes code, recomputes SHA-256 hash, and captures target settings from internal extension storage.
- **Assessment**: Architecture sound; proven in unit/component tests; end-to-end integration verified in Phase 1C.4.3.1.

### B. Malicious / Forged Message Sender
- **Scenario**: An attacker or rogue script sends messages to `browser.runtime.onMessage` claiming privileged sender contexts (`popup`, `background`), wrong message types, malformed envelopes, replayed nonces, or forged origins.
- **Mitigation**: `MessageEnvelopeValidator` derives trusted sender context from browser runtime metadata (`runtimeSender.tab`, `runtimeSender.url`, `runtimeSender.id`). Claimed sender context must match derived context. Allowed actions are restricted by `CONTEXT_ALLOWED_ACTIONS`. UUID v4 nonce and sliding window timestamps reject replays and stale envelopes fail-closed.
- **Assessment**: Architecture sound; 18 dedicated tests in `messaging-envelope.test.ts`.

### C. Forged Validation Authority
- **Scenario**: An attacker crafts an object containing `validatedBy: "SERVICE_WORKER"` or `authority: "EXTENSION_INTERNAL"` with forged tokens.
- **Mitigation**: `SubmissionHandler` never trusts incoming validation fields. It constructs a fresh `NormalizedSubmission` and applies `validatedBy: "SERVICE_WORKER"` internally only after all validation steps succeed. `GitHubQueueSyncHandler` enforces that `item.validatedBy === "SERVICE_WORKER"`. `validateAuthoritativeSource` rejects any payload lacking the private `EXTENSION_AUTHORITY_TOKEN`.
- **Assessment**: Architecture sound; tested in `platform-provenance.test.ts` and `queue-github-handler.test.ts`.

### D. Payload Tampering
- **Scenario**: An attacker alters the source code payload in IndexedDB after enqueue, replaces a payload reference, or creates a mismatch between metadata `contentHash` and payload code.
- **Mitigation**: In Step 2 of `GitHubQueueSyncHandler.handle`, the source code is retrieved from IndexedDB, normalized, and its SHA-256 content hash is recomputed. If `recalculatedHash !== item.contentHash`, execution halts immediately, zero GitHub writes are dispatched, and the item is quarantined to `REQUIRES_ATTENTION` with `INVARIANT_VIOLATION`.
- **Assessment**: Architecture sound; tested in `queue-github-handler.test.ts` (HANDLER-05). Cross-pipeline adversarial test proposed for .5.1.

### E. Target Tampering
- **Scenario**: An attacker attempts to alter repository, owner, branch, base path, or duplicate policy in extension storage after an item is enqueued to hijack the destination repository.
- **Mitigation**: Target settings are captured at enqueue time into an immutable, frozen [TargetSnapshot](file:///d:/Parth/Projects/CodeSync/src/shared/storage/types.ts#L24-L37). `GitHubQueueSyncHandler` reads execution target properties strictly from `item.targetSnapshot`, completely ignoring dynamic extension configuration in `storage.local`.
- **Assessment**: Architecture sound; verified in `queue-drainer.test.ts` (DR-13).

### F. Authorization Confusion
- **Scenario**: An authenticated user configures a repository they do not have push permissions for, or permissions are revoked after enqueue, or installation scope changes.
- **Mitigation**: Local syntax validation does not substitute for GitHub authorization. At drain execution time, `GitHubContentsService` performs live `getRepository(owner, repo)`. If GitHub returns 403 or 404, the item is immediately quarantined into `REQUIRES_ATTENTION` with `GITHUB_FORBIDDEN` or `GITHUB_REPOSITORY_NOT_FOUND`. Zero retries are consumed and no fallback to other repositories occurs.
- **Assessment**: Architecture sound; verified in `queue-github-handler.test.ts` (HANDLER-17). Targeted integration test proposed for .5.1.

### G. Queue Poisoning
- **Scenario**: Malformed queue items with missing UUIDs, invalid platforms, corrupted state transitions, invalid TargetSnapshots, or missing payloads are inserted into storage.
- **Mitigation**: `GitHubQueueSyncHandler` executes a comprehensive 5-step validation gate before any external call: validates `validatedBy`, UUID regex, platform whitelist, content hash format, payload existence, 500KB size limit, hash equality, TargetSnapshot fields, and path safety. Any violation quarantines the item to `REQUIRES_ATTENTION`. Interrupted items exceeding 3 crashes are quarantined by `reconcileInterruptedItems` as poison pills.
- **Assessment**: Architecture sound; extensively tested in `queue-github-handler.test.ts` (HANDLER-01 through 05) and `queue-drainer.test.ts`.

### H. Stale Worker / Fencing Attack
- **Scenario**: Worker A acquires a lease, stalls (e.g. GC pause or network hang), Worker B takes over after lease expiry with an incremented fencing token, and Worker A resumes attempting to mutate state, delete WAL entries, or record completion.
- **Mitigation**: Every durable state transition, WAL deletion, error write, and outcome commit in `QueueManager` validates `concurrency.validateFencingToken(workerId, fencingToken)`. Stale workers throw `StaleLeaseError` fail-closed.
- **Assessment**: Architecture sound; verified in `persistent-lease-fencing.test.ts` (FENCE-INT-01 to 04) and `idempotency-duplicate-conflict.test.ts` (IDEM-INT-03, IDEM-INT-04).

### I. Race Between Check and Mutation (TOCTOU)
- **Scenario**: A security check succeeds, but state changes before the corresponding mutation occurs (e.g. remote file changes between pre-flight GET and PUT, or authorization revokes between check and write).
- **Mitigation**:
  - Remote file changes: GitHub's API enforces server-side OCC via blob SHA. If remote content changed, GitHub returns HTTP 409 Conflict. CodeSync's 409 protocol re-fetches fresh SHA and re-evaluates duplicate policy.
  - Queue mutations: Protected by persistent lease fencing tokens.
  - Post-write: Verification GET validates that the remote commit matches local content hash before marking complete.
- **Assessment**: Architecture sound; OCC and verification protocol verified in `idempotency-duplicate-conflict.test.ts` (IDEM-INT-03) and `pipeline-e2e.test.ts`.

### J. GitHub Conflict / OCC Abuse
- **Scenario**: External actors commit conflicting changes causing repeated 409s, stale SHAs, or `KEEP_ALL` collisions.
- **Mitigation**: 409 revalidations are bounded at `MAX_CONFLICT_REVALIDATIONS = 2`. Exceeding the bound quarantines to `REQUIRES_ATTENTION`. `KEEP_ALL` candidate probing is strictly bounded at `MAX_KEEP_ALL_CANDIDATES = 10` (-v2 to -v10) and fails closed into `REQUIRES_ATTENTION` with zero PUT writes (verified in `IDEM-INT-02`).
- **Assessment**: Architecture sound; fully proven in Phase 1C.4.3.4.1 (`IDEM-INT-02`, `IDEM-INT-03`).

### K. Uncertain Write Abuse
- **Scenario**: Network drops or timeouts occur while a PUT request is in flight. A blind retry could cause duplicate commits or corrupted Git history.
- **Mitigation**: `GitHubContentsService` catches transport errors and executes `reconcileUncertainWrite` via fresh authoritative GET. If remote hash matches, it confirms success; if remote does not match or is absent, it throws `GitHubWriteOutcomeUnknownError`. `GitHubQueueSyncHandler` quarantines to `REQUIRES_ATTENTION` (`GITHUB_WRITE_OUTCOME_UNKNOWN`). Blind duplicate PUTs are strictly forbidden.
- **Assessment**: Architecture sound; proven in `pipeline-e2e.test.ts` (FAIL-MAT-01 to 05) and `idempotency-duplicate-conflict.test.ts` (IDEM-INT-04).

### L. Rate-Limit / Retry Abuse
- **Scenario**: Malicious or extreme `Retry-After` headers, repeated 429/403 secondary rate limits, or worker restarts causing uncontrolled request loops.
- **Mitigation**: Primary (429, 403 remaining=0) and secondary (403 with Retry-After) rate limits are parsed safely. If `Retry-After` is non-numeric, it defaults to 60s. Exponential backoff and `resetTimestamp` dictate `nextRetryAt`. Retries are capped at `MAX_ATTEMPTS = 5`. Subsequent drain passes skip items where `now < nextRetryAt`.
- **Assessment**: Architecture sound; proven in `retry-rate-limit-recovery.test.ts`.

### M. Input / Unicode / Path Abuse
- **Scenario**: Hostile input attempting directory traversal (`../`), encoded traversal (`%2e%2e`), Windows drives (`C:`), UNC paths (`//`), DOS reserved names (`CON`, `NUL`), Git internals (`.git`), Unicode homoglyphs, or overlong paths.
- **Mitigation**: Three-Pillar Path Engine enforces bounded recursive decode, strict ASCII whitelist (`^[a-zA-Z0-9_.-]+$`), absolute rejection of non-ASCII / homoglyphs / control bytes / NUL, DOS device regex, Git protected regex, max depth 10, segment length <= 100, and total length <= 255 with base folder containment.
- **Assessment**: Architecture sound; 32 dedicated tests in `github-path-security.test.ts`.

### N. Replay / Duplicate Event Abuse
- **Scenario**: Replaying identical submission messages, concurrent duplicate submissions, or replaying old events after completion.
- **Mitigation**: Content script dedup suppresses immediate event duplicates. Service worker sliding window and in-memory nonce cache reject envelope replays. Queue manager deduplicates across 3 hierarchies. GitHub pre-flight GET skips identical remote content with `skipped_identical`.
- **Assessment**: Architecture sound; proven in `idempotency-duplicate-conflict.test.ts` (IDEM-INT-01, IDEM-INT-05).

### O. Cross-Platform Confusion
- **Scenario**: A submission message from `codechef.com` claims `platform: "leetcode"` to bypass platform-specific validation or confuse storage.
- **Mitigation**: `SubmissionHandler` cross-references `runtimeSender.tab.url` against `adapter.supportedOrigins`. `validatePlatformOrigin` requires HTTPS, port 443, no userinfo, and exact hostname matching. A mismatch throws `SecurityError(SECURITY_VIOLATION)` immediately.
- **Assessment**: Architecture sound; 15 dedicated tests in `platform-origin-security.test.ts`.

## 9. Integration / Adversarial Evidence Gaps

The audit categorized potential findings into five strict categories:

1. **Confirmed Defects**: **None confirmed (0)**.
2. **Architectural Weaknesses**: **None confirmed (0)**.
3. **Evidence Gaps**: While unit and component isolation tests prove each component independently, the end-to-end interaction across the integrated pipeline contains 5 specific scenarios where full-chain adversarial proof will eliminate any theoretical uncertainty:
   - **GAP-01 (Cross-Origin Message Spoofing Full Chain)**: Verifying that an adversarial message with a spoofed origin or invalid context fails at the service worker without creating residual WAL or queue records, and produces zero GitHub side effects.
   - **GAP-02 (Post-Enqueue Payload Tampering Full Pipeline)**: Verifying that tampering with an IndexedDB source code payload after enqueue stops cleanly at the handler boundary during a live drain pass, quarantines to `REQUIRES_ATTENTION` (`INVARIANT_VIOLATION`), records zero sync history, and issues zero PUT requests to the mock GitHub server.
   - **GAP-03 (Target Authorization Revocation at Drain Time)**: Verifying that when target repository push permissions are revoked between enqueue and drain, the drain pass halts upon the authoritative `getRepository` check (HTTP 403), quarantines immediately to `REQUIRES_ATTENTION` (`GITHUB_FORBIDDEN`), consumes zero retries, and issues zero write calls.
   - **GAP-04 (Adversarial Path Traversal Full Pipeline Rejection)**: Verifying that an adversarial path attempting encoded traversal or DOS device names injected into a submission candidate fails closed before reaching GitHub, producing zero remote writes.
   - **GAP-05 (Stale Worker Fencing Race During Multi-Worker Drain)**: Verifying that a stale worker whose lease expired during GitHub write execution is rejected fail-closed by `validateFencingToken` when attempting to commit completion, preventing queue state corruption or duplicate history entries.
4. **Test Gaps**: The 5 specific integration test scenarios defined in Section 10 below.
5. **Theoretical Threats**: Network-level compromise of GitHub's server-side OCC; out of scope for extension security architecture.

### SEC-INT-05 — Stale Worker Fencing Race During Drain Execution
- **Threat Addressed**: THREAT-H (Stale Worker / Fencing Attack) & THREAT-I (Race Between Check and Mutation)
- **Preconditions**: A queue item is in `PENDING` state. Worker A acquires persistent lease (token 1) and claims the item into `PROCESSING`.
- **Attack / Interleaving**: Worker A begins `handler(item, payload)`. While Worker A is inside the handler, Worker A's lease expires (simulated by manually superseding the lease with Worker B, token 2). Worker A finishes the handler and attempts to commit completion state to storage.
- **Production Path**: [QueueManager.drainQueue](file:///d:/Parth/Projects/CodeSync/src/shared/queue/manager.ts) (Step 491 fencing check: `validateFencingToken`).
- **Expected Security Behavior**: Worker A's attempt to commit outcome triggers `validateFencingToken(workerA, 1)`, which detects that authoritative lease is now owned by Worker B (token 2) and throws `StaleLeaseError`. Worker A is completely blocked from marking the item `COMPLETED` or appending to `codesync_db:sync_history`.
- **Expected Queue State**: Queue state remains as left by authoritative authority; Worker A's stale mutation is rejected.
- **Expected GitHub Side Effects**: Zero duplicate writes from Worker A.
- **Why Existing Tests Are Insufficient**: `persistent-lease-fencing.test.ts` tests fencing at the handler-error boundary, but does not test the exact post-handler completion commit boundary under an integrated drain execution.
- **Pass/Fail Criteria**: `StaleLeaseError` thrown; stale worker cannot commit `COMPLETED`; history table untouched by stale worker.
