# Phase 1C.3 Completion Report: Platform Adapter Architecture & Submission Detection

## 1. Executive Summary

Phase 1C.3 introduces CodeSync's strongly-typed **Platform Adapter Subsystem** and **Submission Detection Architecture**. It enables CodeSync to detect submission interactions and extract canonical submission candidates across four initial competitive programming platforms: **LeetCode**, **CodeChef**, **Codeforces**, and **GeeksforGeeks**.

The implementation preserves the foundational trust model:
```text
Webpage (UNTRUSTED) → Content Script (SEMI-TRUSTED) → Service Worker (AUTHORITATIVE) → GitHub (EXTERNAL)
```
Platform adapters operate as semi-trusted extractors producing **candidate data, not authorization**. Extracted submissions are normalized, deduplicated against event floods, encapsulated in replay-protected extension messages with UUID v4 nonces, and authoritatively re-validated in the background service worker.

Zero automatic GitHub syncing, zero automatic queue draining, zero PAT fallbacks, and zero broad permissions (`<all_urls>`, `webRequest`) were introduced.

---

## 2. Architecture

```text
       Platform Webpage (DOM Mutation / Click Events)
                             ↓
 Content Script Runner (Bounded Listeners, LRU Event Deduplication)
                             ↓
 Platform Adapter (LeetCode / CodeChef / Codeforces / GeeksforGeeks)
                             ↓
 Canonical Submission Candidate (Platform-Independent, UTF-8 Normalized, SHA-256 Hashed)
                             ↓
 Secure Extension Messaging Envelope (UUID v4 Nonce, Freshness Window, Anti-Replay)
                             ↓
 Service Worker SubmissionHandler (Authoritative Schema & Origin Verification)
```

1. **Content Script Layer**: Evaluates `window.location.href` against the extension-controlled `PlatformAdapterRegistry`. If matching, it hooks bounded click listeners and MutationObservers on platform-specific result containers.
2. **Adapter Layer**: Implements `canHandle`, `detectSubmission`, and `extractSubmission`. Uses layered extraction (result banner → editor view-lines → textarea fallback).
3. **Canonical Normalization**: Standardizes source code to canonical UTF-8, normalizes CRLF/CR to LF, strips trailing line whitespace, enforces a single trailing newline, and computes the canonical SHA-256 content hash using the existing hashing subsystem.
4. **Service Worker Layer**: Receives `SUBMISSION_DETECTED` message, validates envelope nonce and freshness window, verifies that the browser runtime tab URL matches the claimed platform adapter's approved origins, and verifies schema bounds fail-closed.

## 6. Security

### Origin Validation
Every adapter defines an immutable `supportedOrigins` array of canonical origins. Validation uses `URL` structural parsing (`parsed.origin`) with exact scheme and hostname equality matching. Subdomain wildcards and loose substring matching (`url.includes("leetcode")`) are strictly forbidden. Lookalike domains (`leetcode.com.evil.test`, `evil-leetcode.com`) are systematically rejected.

### Trust Separation
- **Webpage (UNTRUSTED)**: The webpage DOM can be manipulated by malicious scripts or extensions.
- **Content Script (SEMI-TRUSTED)**: Gathers DOM state, runs deduplication, but has zero write authority.
- **Service Worker (TRUSTED)**: Authoritative boundary. Validates incoming message sender context via the browser runtime (`runtimeSender.tab`), cross-references the tab URL with the claimed platform, and enforces full schema validation.
- **GitHub (EXTERNAL)**: Remote target. Never receives writes from content scripts directly.

### Input Validation
All fields extracted from pages are treated as untrusted strings. The `validateCanonicalSubmission` routine validates:
- `platform`: Must be in `SUPPORTED_PLATFORMS` allowlist.
- `status`: Must be in `CANONICAL_STATUSES` allowlist.
- `problemId`: Non-empty, alphanumeric/dash/underscore, max 128 chars.
- `problemTitle`: Max 256 chars, stripped of control characters.
- `language`: Max 64 chars.
- `sourceCode`: Non-empty, max `MAX_SOURCE_PAYLOAD_BYTES` (500KB), zero ASCII control characters (`\0` through `\x08`, `\x0B`, `\x0E` through `\x1F`).

### URL Validation
All candidate URLs (`problemUrl`, `sourceUrl`) are parsed via `new URL()`. Only `http:` and `https:` protocols are accepted. Dangerous schemes (`javascript:`, `data:`, `blob:`, `file:`) throw immediate `SecurityError`.

### Source Code Handling
Extracted source code is treated strictly as plain text. It is never evaluated (`eval`), never passed to `new Function()`, and never rendered using `innerHTML`.

### Permissions
Zero unnecessary permissions were added. CodeSync maintains its existing manifest with **zero** `<all_urls>`, **zero** `webRequest`, **zero** `webRequestBlocking`, **zero** `cookies`, **zero** `tabs`, and **zero** `scripting` permissions.

### Anti-Replay & Message Protection
Every submission event message sent across extension contexts carries:
- A cryptographically random UUID v4 nonce (`crypto.randomUUID()`)
- A high-resolution numeric timestamp validated against a sliding freshness window (max age 30s, max future skew 5s)
- Sender context verified through runtime metadata
- In-memory anti-replay tracking ensuring no message nonce is processed twice

### Authorization Invariant
Extracted candidates from webpages **cannot authorize GitHub operations**. Candidate data is purely diagnostic and ingestive. Downstream sync requires authoritative user authentication, explicit policy approval, repository configuration, and queue processing.

## 10. Known Limitations

1. **DOM Structure Volatility**: Coding platforms frequently deploy frontend updates that rename or shuffle DOM classes. While adapters employ multi-selector fallbacks (e.g. Monaco editor view lines falling back to native textareas), substantial redesigns on a target site may require adapter selector updates.
2. **Dynamic SPA Hydration**: Certain single-page platforms (e.g. modern LeetCode contest interfaces) dynamically re-render result DOM nodes asynchronously; detection relies on MutationObservers and may require user interaction (e.g. clicking "Submit" or navigating to the result tab) if result nodes are mounted lazily.
3. **No Network-Level Interception**: By design, CodeSync avoids `webRequest` interception to respect least-privilege security. Consequently, platforms where source code is wiped from the DOM immediately upon submission without retaining a visible editor require page-context fallback extraction.
