## 3. QueueDrainer Architecture

```
External Triggers
  ├── Message (SUBMISSION_DETECTED -> valid enqueue)  → TriggerSource: "submission_event"
  ├── Startup (Worker Wake / onInstalled / onStartup) → TriggerSource: "startup"
  └── Alarm (browser.alarms codesync_queue_drain_alarm) → TriggerSource: "alarm"
         │
         ▼
  QueueDrainer.drain(triggerSource)
         │
         ▼
  QueueManager.drainQueue(triggerSource, effectiveHandler)
         │
         ├── Concurrency Guard: QueueConcurrencyManager.runExclusively
         │     ├── Tier 1: Web Lock 'codesync_queue_drain' (Active Mutex)
         │     └── Tier 2: Persistent Storage Lease 'codesync:queue_lease' (30s TTL, fencingToken)
         │
         ├── Crash Recovery: reconcileInterruptedItems() (crashCount >= 3 -> REQUIRES_ATTENTION)
         │
         ├── WAL & Orphan Reconciliation: reconcileWalAndOrphans()
         │
         ├── Sequential Item Eligibility: PENDING or (FAILED && nextRetryAt <= now)
         │
         ├── Pre-mutation Fencing Check: validateFencingToken(workerId, fencingToken)
         │
         ├── State -> PROCESSING (stamped with fencingToken)
         │
         ├── Payload Retrieval from IndexedDB (PayloadStorage)
         │
         ├── Invocation: effectiveHandler(item, payload)
         │     └── Default Handler (Phase 1C.4.2.1): Safe fallback, no GitHub write
         │     └── Future Handler (Phase 1C.4.2.2): GitHubContentsService.synchronizeFile(...)
         │
         ├── Post-handler Fencing Check: validateFencingToken(workerId, fencingToken)
         │
         ├── Durable State Mutation: COMPLETED / SKIPPED / FAILED / REQUIRES_ATTENTION
         │
         └── Lease Heartbeat Renewal (every 10s) & Orderly Release
```

## 4. Background Trigger Integration

All triggers execute strictly within the trusted service worker execution context:

1. **Submission Event Trigger (`"submission_event"`)**:
   - In [src/entrypoints/background.ts](file:///d:/Parth/Projects/CodeSync/src/entrypoints/background.ts#L93-L125), `browser.runtime.onMessage` listens for `SUBMISSION_DETECTED`.
   - It invokes `defaultSubmissionHandler.handleMessageAndEnqueue(...)`.
   - **Guarded Execution**: `defaultQueueDrainer.drain("submission_event")` is initiated **only** if `result.success && result.queueItem`. If validation or WAL enqueue fails, no drain is triggered.
   - `sendResponse(result)` returns immediately to content scripts; drain execution proceeds asynchronously in the background.

2. **Startup & Recovery Trigger (`"startup"`)**:
   - Service worker activation: `defaultQueueDrainer.drain("startup")` executes immediately upon top-level service worker wake.
   - Extension install / update: `browser.runtime.onInstalled` triggers `defaultQueueDrainer.drain("startup")`.
   - Browser startup: `browser.runtime.onStartup` triggers `defaultQueueDrainer.drain("startup")`.
   - Multiple startup events safely coalesce under `runExclusively`.

3. **Alarm Trigger (`"alarm"`)**:
   - `setupQueueDrainAlarm()` checks `browser.alarms.get(QUEUE_DRAIN_ALARM_NAME)` and only creates the alarm if absent (`periodInMinutes: 5`).
   - `browser.alarms.onAlarm` checks `alarm.name === QUEUE_DRAIN_ALARM_NAME` and invokes `defaultQueueDrainer.drain("alarm")`.

4. **Network Recovery Trigger**:
   - As audited in Phase 1C.4.2.0, the extension has no pre-existing network monitoring subsystem. Per Phase 1C.4.2.1 instructions, no ad-hoc network listener was created; network recovery remains scheduled for periodic alarm or future phases.

## 5. Concurrency Analysis

No second locking system or custom state variables (such as `isDraining: boolean`) were introduced into `QueueDrainer`.

### Rationale:
- Creating a local lock in `QueueDrainer` would create split-brain vulnerabilities across service worker wakeups, multiple extension contexts, or concurrent background tasks.
- `QueueManager.drainQueue` already provides an audited, two-tier concurrency architecture:
  1. **Tier 1 (In-Memory / In-Session)**: Web Locks API (`navigator.locks.request("codesync_queue_drain", { mode: "exclusive", ifAvailable: true })`) guarantees active mutual exclusion.
  2. **Tier 2 (Durable / Cross-Session)**: Persistent storage lease (`codesync:queue_lease`) with monotonic `fencingToken`, Probe-and-Verify verification read-back, and 30-second TTL prevents split-brain across crashes or service worker terminations.
- Any concurrent drain trigger arriving while a drain pass is active yields gracefully (`null`) at the `QueueManager` boundary.

## 8. Rate-Limit Finding (P2 Resolution)

**Status: FIXED SAFELY NOW**

Phase 1C.4.2.0 identified `FINDING-1C42-03`: `QueueManager` previously computed retry delay strictly using generic exponential backoff, ignoring future rate limit reset timestamps.

### Implementation:
1. Extended [SyncResult.error](file:///d:/Parth/Projects/CodeSync/src/shared/queue/types.ts#L44-L45) with optional `resetTimestamp?: number` and `retryAfterSeconds?: number`.
2. Updated [QueueManager.drainQueue](file:///d:/Parth/Projects/CodeSync/src/shared/queue/manager.ts#L514-L526):
   ```typescript
   const backoffDelay = computeBackoffDelay(item.attempts);
   let rateLimitDelay = 0;
   if (result.error?.resetTimestamp) {
     rateLimitDelay = Math.max(0, result.error.resetTimestamp - Date.now());
   } else if (result.error?.retryAfterSeconds) {
     rateLimitDelay = result.error.retryAfterSeconds * 1000;
   }
   const effectiveDelay = Math.max(backoffDelay, rateLimitDelay);
   item.nextRetryAt = Date.now() + effectiveDelay;
   ```
3. Rate-limit classification remains entirely in `GitHubApiClient`. No duplicate parsing was introduced into `QueueManager`.
4. Verified by **DR-15** and **DR-16**.
