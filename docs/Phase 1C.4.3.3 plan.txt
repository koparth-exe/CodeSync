# Phase 1C.4.3 — Architecture / Integration Contract

## Objective

**Phase 1C.4.3 — End-to-End Reliability, Reconciliation & Operational Hardening**

The purpose of 1C.4.3 should be to take the now-working:

```text
Submission
   ↓
Adapter
   ↓
Durable WAL / Queue
   ↓
QueueDrainer
   ↓
GitHubQueueSyncHandler
   ↓
GitHubContentsService
   ↓
GitHub
```

and harden the **entire end-to-end pipeline** against the difficult real-world cases that cannot be adequately proven by isolated component tests.

This is **not** a new feature phase. It is a reliability/security/integration phase.

---

# 1. Architectural baseline

The following are frozen and must not be redesigned:

### 1C.4.1
- submission → durable queue
- intent-first WAL
- immutable `TargetSnapshot`
- submission identity
- provenance
- queue recovery

### 1C.4.2.1
- `QueueDrainer`
- centralized drain triggers
- Web Locks + durable lease
- fencing
- 5-minute alarm
- fail-closed no-handler behavior

### 1C.4.2.2
- `GitHubQueueSyncHandler`
- queue → GitHub integration
- 500 KB payload limit
- content-hash verification
- path validation
- authorization boundary
- `GitHubContentsService`
- OCC
- duplicate policies
- verification
- uncertain-write handling

**1C.4.3 must integrate and harden these systems—not replace them.**

---

# 2. What 1C.4.3 should solve

We now need to prove that the system behaves correctly when multiple components interact.

The key question changes from:

> "Does each component work?"

to:

> **"Does CodeSync remain correct when the entire system is subjected to crashes, races, retries, duplicate triggers, network failures, authorization changes, and recovery?"**

# 6. Crash / restart testing

This is one of the most important parts.

We need to simulate service-worker termination at meaningful boundaries:

```text
A  before queue claim
B  after claim
C  during handler validation
D  immediately before GitHub request
E  after GitHub dispatch
F  after GitHub response
G  before verification
H  after verification
I  before queue completion
J  after history persistence
```

For each boundary, verify:

- no permanent queue loss
- no duplicate unsafe GitHub write
- WAL recovery works
- stale workers cannot mutate state
- fencing remains authoritative
- uncertain writes remain uncertain
- completed operations aren't unnecessarily repeated

---

# 7. Idempotency verification

We need to distinguish three different things:

```text
Submission identity
        ≠
Content identity
        ≠
Repository state
```

Examples:

### Same submission, same content

Should not produce duplicate synchronization.

### Different submissions, same content

Must remain distinct queue submissions.

### Same submission, changed remote file

Must follow the configured duplicate/OCC policy.

### Same submission after service-worker restart

Must not create an unsafe duplicate write.

---

# 8. Concurrent trigger testing

Test:

```text
submission_event
      +
startup
      +
alarm
```

arriving simultaneously.

Expected:

```text
3 triggers
   ↓
central QueueDrainer
   ↓
QueueManager concurrency control
   ↓
one authoritative processing path
```

No duplicate processing.

No duplicate commits.

No fencing violations.

---

# 9. Adversarial security integration

We should test malicious data **across layers**, not just individual validators.

For example:

```text
malicious page
    ↓
forged submission message
    ↓
queue metadata
    ↓
GitHub handler
```

Attempt to inject:

- forged `validatedBy`
- forged provenance
- fake submission ID
- malicious repository
- malicious branch
- traversal path
- encoded traversal
- Unicode normalization tricks
- oversized payload
- hash mismatch
- malformed TargetSnapshot
- stale authorization
- replayed message
- stale worker/fencing token

Expected principle:

> **No untrusted input should be able to cross the service-worker security boundary and cause an unauthorized GitHub write.**

---

# 10. Cross-browser verification

Because CodeSync is explicitly cross-browser, 1C.4.3 should verify:

### Chrome MV3

```text
content → worker → queue → GitHub
```

### Firefox MV3

Same flow.

Specifically verify differences around:

- `browser.runtime`
- `browser.alarms`
- service-worker lifecycle
- storage
- Web Locks availability/fallback
- extension messaging

We should **not assume Chrome success implies Firefox correctness.**

---

# 11. Operational invariants

At the end of 1C.4.3, these should all be mechanically testable:

```text
UNTRUSTED PAGE ≠ TRUSTED CODE

CONTENT SCRIPT ≠ SERVICE WORKER

SUBMISSION ID ≠ CONTENT HASH

EXTRACTION PROVENANCE ≠ VALIDATION AUTHORITY

TARGET CONFIGURATION ≠ GITHUB AUTHORIZATION

QUEUE CLAIM ≠ GITHUB WRITE

HTTP DISPATCH ≠ SUCCESS

UNKNOWN WRITE ≠ FAILURE

UNKNOWN WRITE ≠ SUCCESS

VERIFICATION UNKNOWN ≠ CONFIRMED

RETRY ≠ BLIND REWRITE

409 ≠ BLIND OVERWRITE

STALE WORKER ≠ MUTATION AUTHORITY
```

These are effectively our **core security/correctness invariants**.

---

# 12. Observability / diagnostics

We should verify that operational diagnostics provide enough information to answer:

> "Why didn't this submission reach GitHub?"

without exposing sensitive data.

Diagnostics should be able to distinguish:

```text
DETECTED
QUEUED
PROCESSING
COMPLETED
SKIPPED
RETRYING
REQUIRES_ATTENTION
```

and appropriate error categories.

But:

❌ no source-code dumps  
❌ no tokens  
❌ no cookies  
❌ no authorization headers  
❌ no sensitive page content

---

# 13. Performance / API discipline

1C.4.3 should also test that normal operation does not accidentally generate excessive GitHub traffic.

For example:

```text
one submission
    ↓
one controlled synchronization workflow
```

rather than:

```text
one submission
    ↓
multiple triggers
    ↓
multiple GETs
    ↓
multiple PUTs
    ↓
retry storm ❌
```

The existing rate-limit architecture must remain authoritative.
