3. Identity Model
================================================================================

CodeSync enforces a strict, four-pillar identity model. Each identity tier serves
a distinct operational role and is never conflated or substituted with another.

--------------------------------------------------------------------------------
A. Submission Identity (Authoritative Platform Submission)
--------------------------------------------------------------------------------
- Definition: Platform namespace + platform submission identifier:
  `platform + submissionId` (e.g., `"leetcode:11235813"`).
- Fallback: Only when a platform does not provide a durable submission ID on both
  items does CodeSync fall back to `platform + problemSlug + contentHash`.
- Invariant:
  SUBMISSION IDENTITY != CONTENT IDENTITY.
  Two submissions with different submission IDs (e.g., `sub-101` and `sub-102`)
  represent distinct platform submission events. They MUST NEVER be collapsed or
  deduplicated in the queue, even if their source code, normalized content hash,
  problem slug, and target repository are 100% identical.

--------------------------------------------------------------------------------
B. Content Identity (Normalized Cryptographic Hash)
--------------------------------------------------------------------------------
- Definition: SHA-256 hexadecimal hash (64 lowercase hex chars) computed over
  deterministically normalized source code:
  1. Unicode canonicalization (NFKC normalization).
  2. Line ending normalization (CRLF and CR -> POSIX LF).
  3. Trailing whitespace stripping per line (`/[ \t]+$/`).
  4. Bounded trailing newline stripping (exactly one terminal `\n` at EOF).
- Implementation: `computeContentHash` via native Web Crypto (`crypto.subtle.digest("SHA-256")`).
- Role: Content equivalence checks and GitHub write policy evaluation
  (`REPLACE_IF_DIFFERENT`), but NEVER a replacement for platform submission identity.

--------------------------------------------------------------------------------
C. Target Identity (Immutable Destination Snapshot)
--------------------------------------------------------------------------------
- Definition: `TargetSnapshot` immutably captured and frozen at enqueue time:
  - `targetRepository`: Validated `owner/repo` (e.g., `"octocat/leetcode-solutions"`).
  - `targetBranch`: Validated Git ref branch name (e.g., `"main"`).
  - `basePath`: Validated canonical base directory (e.g., `"solutions"`).
  - `duplicatePolicy`: Authoritative policy (`"REPLACE_IF_DIFFERENT" | "KEEP_ALL" | "CREATE_ONLY" | "ALWAYS_REPLACE"`).
  - `authorizationStatus`: Authorization state at snapshot capture.
- Invariant:
  The same submission targeted at Repo A/path X is NOT the same synchronization
  operation as the same submission targeted at Repo B/path Y. The snapshot prevents
  subsequent settings changes from mutating inflight queue work.

--------------------------------------------------------------------------------
D. Remote File Identity (GitHub Object Model)
--------------------------------------------------------------------------------
- Definition:
  - `fileSha`: Git blob SHA-1 (`sha1("blob " + size + "\0" + content)`).
  - `commitSha`: Git commit object SHA-1.
- Invariant:
  Remote blob SHA is an opaque Git object identifier used strictly for Optimistic
  Concurrency Control (OCC) during HTTP PUT requests (`sha: currentSha`). It is
  NEVER confused with local SHA-256 contentHash, queue item UUID, or platform
  submissionId.

--------------------------------------------------------------------------------
E. Queue Item Identity (Internal Durable Work Item)
--------------------------------------------------------------------------------
- Definition: UUID v4 `id` uniquely identifying the queue item metadata record
  in `storage.local`, associated with heavy payload `payload:<uuid>` in IndexedDB.

4. Queue Idempotency
================================================================================

Audit of `QueueManager.enqueueSubmission` (`src/shared/queue/manager.ts`):

1. Duplicate Predicate:
   Evaluated against active items (`PENDING` or `PROCESSING`):
   - Hierarchy 1: Exact internal queue item ID match (`raw.id && i.id === raw.id`).
   - Hierarchy 2: Platform submission ID match (`raw.submissionId && i.submissionId && i.platform === raw.platform && i.submissionId === raw.submissionId`).
   - Hierarchy 3: Fallback when both lack submissionId (`!raw.submissionId && !i.submissionId && i.platform === raw.platform && i.problemSlug === raw.problemSlug && i.contentHash === contentHash`).
   - If match is found: returns existing `QueueItemMetadata` immediately without modifying storage or WAL.

2. Determinism & Persistence:
   The predicate is fully deterministic and operates over durable metadata in
   `chrome.storage.local`. It does not rely on transient in-memory state.

3. Restart Safety:
   - Worker Restart: Metadata persists across service worker lifecycle. New worker
     queries `storage.getQueueMetadata()` and detects active items.
   - Browser Restart: `storage.local` survives browser restarts. Enqueue attempts
     after browser launch correctly detect existing active items.

4. Concurrency & Atomicity:
   - `enqueueSubmission` reads metadata, checks duplicates, writes WAL INTENT,
     writes IndexedDB payload, and commits metadata to `storage.local`.
   - In MV3 service worker, JavaScript event-loop concurrency could theoretically
     interleave two identical enqueue calls before `storage.setQueueMetadata()`.
     Both would write WAL INTENT records with different UUIDs.
   - However, during drain or WAL reconciliation, items are processed under
     exclusive lease lock, and GitHub Contents write skips identical remote content.

5. WAL / Crash Idempotency
================================================================================

Audit of Write-Ahead Log (`wal.ts`, `manager.ts`):

1. Crash Boundaries:
   - Crash Boundary A (Pre-WAL): No state mutated. Operation safely retried.
   - Crash Boundary B (WAL INTENT written, payload absent): Reconciler cleans up
     orphaned WAL record. Zero corrupt state.
   - Crash Boundary C (Payload written, metadata missing): Reconciler recovers
     metadata in `PENDING` state with `crashCount = 1`. User code is preserved.
   - Crash Boundary D (Metadata written, WAL deletion pending): Reconciler detects
     committed metadata and deletes residual WAL record idempotently.

2. Critical Scenario: Remote Success + Local Crash + Worker Restart:
   - Worker A performs GitHub PUT successfully (file committed on remote).
   - Worker A crashes or terminates before updating queue metadata to `COMPLETED`.
   - Worker B starts, acquires lease, runs `reconcileInterruptedItems` (resets item
     from `PROCESSING` to `PENDING`).
   - Worker B invokes handler -> `GitHubContentsService.synchronizeFile`.
   - STEP 6: Pre-flight GET retrieves the file just committed by Worker A.
   - STEP 7: Duplicate policy evaluation (`REPLACE_IF_DIFFERENT`):
     `remoteFile.contentHash.toLowerCase() === localContentHash.toLowerCase()`.
   - Result: Returns `status: "skipped_identical"`. Zero redundant PUTs issued!
   - Handler maps `skipped_identical` to queue `SyncResult` `status: "skipped"`.
   - QueueManager marks item `SKIPPED`, logs history entry.
   - Conclusion: ZERO blind duplicate writes. Safe, idempotent recovery.

3. Uncertain Outcome Handling (Transport Timeout / Network Drop during PUT):
   - STEP 11: `reconcileUncertainWrite` performs immediate authoritative GET.
   - If remote content matches `localContentHash`: write succeeded -> returns `updated` or `created` with `verificationStatus: "CONFIRMED"`, `dispatchStatus: "uncertain"`.
   - If remote content is absent or differs: throws `GitHubWriteOutcomeUnknownError`.
   - Handler catches error, returns `status: "requires_attention"`, `attentionReason: "GITHUB_WRITE_OUTCOME_UNKNOWN"`.
   - Halts further writes. ZERO blind retries.

6. GitHub Conflict Architecture
================================================================================

Audit of `GitHubContentsService.synchronizeFile` (`src/shared/github/contents-service.ts`):

1. Pre-flight GET (STEP 6):
   - Authoritative GET /repos/{owner}/{repo}/contents/{path}?ref={branch}.
   - Obtains current remote blob SHA (`currentSha`) and remote content.

2. Optimistic Concurrency Control (OCC) PUT (STEP 8):
   - Sends `sha: currentSha` in request body (undefined if creating new file).
   - If remote file was modified concurrently, GitHub rejects with HTTP 409 Conflict.

3. 409 Conflict Protocol (STEP 9):
   - Catches `GitHubConflictError`.
   - Increments `revalidationCount`.
   - Enforces bound: `revalidationCount <= MAX_CONFLICT_REVALIDATIONS` (maximum 2 revalidations).
   - If exceeded: halts immediately, returns `status: "requires_attention"` with `attentionReason: "GITHUB_CONFLICT"`.
   - If bounded:
     - Performs fresh authoritative GET bypassing cache.
     - Re-evaluates duplicate policy with fresh remote content:
       - If fresh content now matches local content -> returns `skipped_identical`.
       - If `CREATE_ONLY` and file exists -> returns `skipped_exists`.
     - Updates `currentSha` to newly obtained authoritative remote blob SHA.
     - Loops back to Step 8 to re-attempt PUT with fresh SHA.

4. KEEP_ALL Candidate Resolution:
   - Invokes `resolveKeepAllPath(owner, repo, branch, initialPath)`.
   - Probes base path; if exists, generates candidate filenames `-v2`, `-v3`, ... `-v10`.
   - Bounded by `MAX_KEEP_ALL_CANDIDATES = 10`.
   - Fail-Closed: If all 10 slots are occupied, THROWS `GitHubApiError` with `ErrorCode.GITHUB_CONFLICT`.
   - Never silently overwrites the last candidate or loops indefinitely.

7. Concurrent Worker Analysis
================================================================================

Audit of two-worker interactions (Worker A vs. Worker B):

- CASE 1: Both receive same submission event.
  -> `SubmissionEventDeduplicator` suppresses duplicate event in content script / adapter.
  -> Envelope validator rejects replayed UUID v4 nonces fail-closed.

- CASE 2: Both attempt to enqueue same submission.
  -> Hierarchy 2 duplicate detection matches `platform + submissionId`.
  -> Second call returns existing active item metadata without creating duplicate work.

- CASE 3: Both attempt to drain the same queue item.
  -> Concurrency lock (`QueueConcurrencyManager.runExclusively`) acquires Web Lock
     and persistent durable lease with monotonically increasing `fencingToken`.
  -> Only one worker holds the lease; second worker's lease acquisition fails gracefully.

- CASE 4: Worker A owns lease and crashes.
  -> Worker A's heartbeat ceases.
  -> Lease expires after TTL (30,000 ms).

- CASE 5: Worker B takes over after lease expiry.
  -> Worker B detects expired lease in `storage.local`.
  -> Worker B reclaims lease, increments `fencingToken` monotonically (e.g. 1 -> 2).
  -> Reconciles interrupted `PROCESSING` items back to `PENDING`.

- CASE 6: Worker A's PUT succeeds remotely, but Worker A crashes before queue update.
  -> Remote file contains new commit. Queue metadata still shows `PROCESSING`.

- CASE 7: Worker B sees item after restart.
  -> Worker B resets item to `PENDING` with `crashCount = 1`.
  -> Pre-flight GET fetches remote file.
  -> `REPLACE_IF_DIFFERENT` observes `remote.contentHash === localContentHash`.
  -> Returns `skipped_identical`; queue completes cleanly with zero duplicate PUTs.

- CASE 8: Both workers observe different remote SHAs.
  -> Only the active lease holder can dispatch writes.
  -> If external actor modified file, OCC PUT fails with 409 and triggers revalidation.

- CASE 9: Worker A has stale remote SHA and Worker B changes file.
  -> Worker A's PUT is rejected by GitHub with HTTP 409 Conflict.
  -> Stale Worker A's fencing token is also superseded if lease was reclaimed.

- CASE 10: Both encounter 409.
  -> Handled sequentially under lease lock; bounded at 2 revalidations.
  -> Escalates to `REQUIRES_ATTENTION` if unresolvable.

- CASE 11: Stale worker attempts post-conflict write.
  -> `validateFencingToken(workerId, fencingToken)` throws `StaleLeaseError` before
     storage mutation. Stale write is rejected.

- CASE 12: Reconciliation result arrives after another worker advanced state.
  -> Fencing check fails closed; stale worker cannot commit obsolete outcome.
