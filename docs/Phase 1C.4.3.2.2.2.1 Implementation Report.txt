## 4. WAL-REC-01 — Interrupted Recovery Pass

### Scenario & Objective
Prove that recovery itself is crash-safe across the boundary between metadata reconstruction and WAL cleanup.

### Initial Durable State
- **WAL Store (IndexedDB `wal_logs`)**: Contains `WalEntry` (`id: opId`, `phase: WalPhase.INTENT`, `snapshot: { submission }`).
- **Payload Store (IndexedDB `payloads`)**: Contains payload `payload:<entityId>` with valid source code.
- **Queue Metadata (`browser.storage.local`)**: Completely absent (`[]`).

### Execution & Crash Boundary
1. **Worker A**: Boots as an independent execution context and starts `reconcileWalAndOrphans()`.
2. **Controlled Crash**: Worker A was intercepted at the exact mutation boundary between metadata persistence and WAL deletion (`deleteWalEntry`).
3. **Observation**:
   - In [`src/shared/queue/manager.ts:258-262`](file:///d:/Parth/Projects/CodeSync/src/shared/queue/manager.ts#L258-L262):
     ```typescript
     queue.push(recoveredMetadata);
     existingQueueIds.add(wal.entityId);
     reconciledWalCount++;
     await this.payloadStorage.deleteWalEntry(wal.id); // Line 262: WAL deleted in IndexedDB
     ...
     await this.storage.setQueueMetadata(queue); // Line 339: Metadata persisted to storage.local
     ```
   - When Worker A terminates before line 262 (`deleteWalEntry`), metadata in `storage.local` has **not** been persisted yet because `setQueueMetadata` is deferred until line 339.
   - When Worker A terminates after line 262, the WAL record has been deleted from IndexedDB, but metadata in `storage.local` has still **not** been written.
4. **Failure Detail**:
   `expected [] to have a length of 1 but got +0` at line 107.
   Durable metadata was `[]` because the production code performs `deleteWalEntry` *before* `setQueueMetadata`.
5. **Result**: **FAILED — EXPOSES PRODUCTION DEFECT**.

## 7. WAL-REC-04 — Stale Recovery Mutation Under Superseded Lease

### Scenario & Objective
Prove that recovery mutation itself is protected by persistent lease and fencing authority, preventing stale workers from mutating durable recovery state after lease supersession (TOCTOU protection).

### Execution & Boundary
1. **Worker A**: Acquires persistent lease with `fencingToken = 1`. Starts recovery pass.
2. **Pause**: Worker A reads the recoverable WAL record and is paused immediately before committing the recovery mutation.
3. **Supersession**: Virtual time advances past lease TTL (35s). Fresh **Worker B** boots, reclaims the expired lease, and acquires `fencingToken = 2`.
4. **Resume**: Worker A unpauses and attempts to complete the recovery mutation.
5. **Observation**:
   - In [`src/shared/queue/manager.ts:206-271`](file:///d:/Parth/Projects/CodeSync/src/shared/queue/manager.ts#L206-L271), `reconcileWalAndOrphans()` has no parameter for `fencingToken` and makes no call to `validateFencingToken`.
   - At line 262, Worker A executes `await this.payloadStorage.deleteWalEntry(wal.id);` *without checking its lease authority*.
   - When Worker A reaches `setQueueMetadata`, Worker A's storage hook enforces fence validation and throws `StaleLeaseError`, but Worker A **had already deleted the durable WAL record** at line 262!
   - As a result, assertion 10 (`expect(await env.getDurableWalEntries()).toHaveLength(1)`) failed (`expected [] to have a length of 1 but got +0`).
   - The WAL was destroyed by the stale worker, leaving Worker B unable to recover the submission.
6. **Result**: **FAILED — EXPOSES PRODUCTION DEFECT**.

## 13. Production Change Assessment

In strict compliance with Section 2 and Section 15 of the prompt:
- **Production source changes**: **0**
- **Test helper changes**: **0**
- **Configuration changes**: **0**

Because production changes were prohibited in this phase, the defects were **not** modified or bypassed. They are formally detailed below:

### Confirmed Production Defect 1: Inverted Write Order in `reconcileWalAndOrphans`
- **File**: [`src/shared/queue/manager.ts`](file:///d:/Parth/Projects/CodeSync/src/shared/queue/manager.ts)
- **Symbol**: `QueueManager.reconcileWalAndOrphans` (lines 258–262, 339)
- **Defect**: The durable WAL record is deleted from IndexedDB at line 262 (`await this.payloadStorage.deleteWalEntry(wal.id)`) *before* the reconstructed queue metadata is persisted to `browser.storage.local` at line 339 (`await this.storage.setQueueMetadata(queue)`).
- **Violated Invariant**: Intent-First Write Ordering: A Write-Ahead Log record must never be deleted before the mutation it logs has been confirmed durable in storage.
- **Security / Correctness Impact**: If a service-worker process terminates between line 262 and line 339, the WAL entry is destroyed while metadata was never written. On restart, the payload exists without metadata or WAL snapshot, permanently losing the submission title, problem slug, platform, target branch, and repository, degrading it to an orphan in `REQUIRES_ATTENTION`.
- **Minimum Required Production Correction**:
  In `src/shared/queue/manager.ts`, move `await this.storage.setQueueMetadata(queue)` to execute *before* deleting the reconciled WAL entries, or delete each WAL entry only after `setQueueMetadata` has durably resolved.

### Confirmed Production Defect 2: Missing Fencing Validation During Recovery Mutations
- **File**: [`src/shared/queue/manager.ts`](file:///d:/Parth/Projects/CodeSync/src/shared/queue/manager.ts)
- **Symbol**: `QueueManager.reconcileWalAndOrphans` (lines 206–271) and `QueueManager.drainQueue` (line 403)
- **Defect**: `reconcileWalAndOrphans()` does not take `workerId` or `fencingToken`, and mutates both IndexedDB (`deleteWalEntry`) and `storage.local` (`setQueueMetadata`) without validating lease authority.
- **Violated Invariant**: `LEASE START AUTHORITY != MUTATION-COMPLETION AUTHORITY` and `STALE WORKER != RECOVERY AUTHORITY`.
- **Security / Correctness Impact**: A superseded, zombie, or suspended worker resuming recovery can delete WAL entries belonging to a newer authoritative worker generation without detection, causing lost writes and recovery race conditions.
- **Minimum Required Production Correction**:
  1. Update `reconcileWalAndOrphans` and `reconcileInterruptedItems` to accept `workerId?: string, fencingToken?: number`.
  2. In `drainQueue`, pass `workerId` and `fencingToken` from `runExclusively` into both reconciliation methods.
  3. Inside `reconcileWalAndOrphans` and `reconcileInterruptedItems`, invoke `await this.concurrency.validateFencingToken(workerId, fencingToken)` prior to committing `deleteWalEntry` or `setQueueMetadata`.
